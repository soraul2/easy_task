# PlanBase 전체 최적화 Goal 실행 프롬프트

작성일: 2026-10-02. [최적화 계획](OPTIMIZATION_2026_10_02_PLAN.md)의 Goal 실행 명세다.
아래 실행 요청을 사용하면 조사·계측·구현·검증·결과 기록까지 진행하는 범위가 된다.
이 문서 작성 시점에는 해당 Goal을 시작하지 않았다. 이후 실행 현황은 연결된 계획의 진행 기록을 따른다.

기준 계획은 build 86의 `b7e524a`에서 작성했지만 실제 실행 기준은 시작 시점의 작업 트리다.

## 실행 요청

PlanBase의 성능과 사용 흐름을 충분히 최적화하는 작업을 하나의 Goal로 설정하고,
전체 조사 → 기준 계측 → 우선순위 결정 → 반복 구현 → 전후 비교 → 회귀·화면 검증 → 결과 기록까지 수행해줘.
계획이나 첫 개선 몇 개에서 멈추지 말고 아래 필수 범위와 완료 조건을 충족할 때까지 자율적으로 진행해.

토큰을 충분히 사용할 의향이 있으므로 조사, 추가 후보 발굴, 반례 검증과 플랫폼 확인에 시간을 투입해.
토큰 예산의 숫자는 지정하지 않았으므로 임의의 숫자를 설정하지 마.
토큰 소진량, 수정 파일 수, 발견 건수나 추측 개선율을 목표로 삼지 말고,
측정과 코드 근거가 있는 개선을 가능한 범위까지 이어가. 실제 자원 한도와 도구 제약은 준수해.

### 2 반드시 조사할 기능 범위

각 영역에서 진입 → 조회 → 계산 → 표시 → 저장 → 후속 갱신을 추적해.
계획에 조사표를 만들고 확인한 파일·함수, 재현 조건, 측정, 관련 테스트와 개선 또는 유지 이유를 기록해.
코드를 바꾸지 않은 영역도 결론을 남겨.

1. 앱 시작·복귀·탭 이동, 무결성 수렴과 성공 import 후 로컬 처리.
2. 칸반 입력·날짜 이동·상태 변경·완료 취소·체크리스트·이월함·진행 시간 표시.
3. 저장한 작업·`/` 빠른 입력·루틴의 검색·편집·재사용·여러 날짜 적용.
4. 캘린더 월·날짜 상세·기간 일정·배치 계산·최근 일정 추천·템플릿 적용.
5. 활동 기록·통계·회고의 조회·검색·필터·페이지·위치 복원과 사진 표시.
6. 메모 글·체크리스트·필기, 생성·자동 저장·실패 복구·검색·미리보기.
7. Focus 시작·일시정지·재개·복원·종료·체크리스트, 알림·Live Activity·deep link·App Intent.
8. iPhone·iPad·Mac 위젯과 Watch 앱·컴플리케이션의 조회·snapshot·표시·갱신.
9. 백업 내보내기·비파괴 병합·실패 rollback과 배포·데이터 호환성.

데이터 손실·잘못된 동작 → 빈번한 입력·탭 지연 → 데이터 증가에 따른 비용 → 반복 계산·쓰기·주기 갱신 순으로 우선순위를 정해.
빈도, 실제 비용, 효과, 검증 가능성과 변경 위험을 함께 평가해.
저비용인 경로를 미세 조정하기보다 사용자 작업을 방해하는 비용을 먼저 줄여.

### 3 현재 코드에서 출발할 후보

아래 항목은 계측 출발점이며 결함이나 구현 확정 목록이 아니다. 새 후보의 효과가 더 크면 근거를 남기고 순서를 바꿔.

- **일반 입력·탭:** `MobileBoardView`의 입력과 상태별 목록·개수·정렬·스크롤 대상 계산을 나눠 계측해.
  날짜 범위 조회 재사용과 비활성 탭 revision은 이미 구현됐으므로 새로 추가하지 마.
  반복 비용이 확인되면 입력 상태 분리나 한 번의 화면 준비에서 결과 공유를 검토해.
- **빠른 입력:** `SavedTaskQuickEntryController`의 최초 라이브러리 준비와 `suggestions` 계산을 분리해.
  같은 query에서 강조 후보만 이동할 때 필터·정렬이 반복되는지 확인해.
  일반 제목 입력에서는 라이브러리 준비를 하지 않는 기존 보호와 실행 직전 최신 데이터 조회는 유지해.
  build 86의 `/` 발견 안내도 이미 완료된 기능이야.
- **메모 저장·검색:** `MemoQuerySession.refresh`의 펼친 페이지 재조회,
  `MemoService.page`의 희소·무결과 검색 배치 수와 메인 실행 영역 점유를 측정해.
  병목이면 요청 병합·취소 가능한 배치·별도 컨텍스트의 값 기반 처리를 검토해.
- **메모 필기:** `MobileMemoView`와 `MemoView`의 같은 revision 미리보기 재렌더,
  모바일 canvas의 반복 `dataRepresentation()` 비용을 계측해.
  확인된 반복에만 캐시·요청 병합·변경 추적을 적용해. 회고 사진 캐시는 이미 구현돼 있어.
- **캘린더·일정 추천:** 월 달력의 날짜 선택과 geometry·데이터 변경을 구분하고 배치 계산 수를 측정해.
  `CalendarEventRecommendationSession`의 동일 세션 입력별 fetch도 확인해.
  세션 한정 재사용을 적용한다면 저장·삭제·성공 import·재시도·날짜·글자 크기의 무효화 조건을 명시해.
- **Focus·보이지 않는 화면:** 실제 tick·snapshot 읽기·진행 projection 수를 확인해.
  SwiftUI가 비가시 갱신을 억제할 수 있으므로 코드만으로 비용을 단정하지 마.
  체크리스트 변경마다 후보 목록·오늘 집계를 다시 읽는 비용을 측정하고 필요한 조회만 갱신하도록 검토해.
- **시작·위젯:** 앱 루트와 publisher의 수렴·조회·snapshot 생성·쓰기·reload 수를 함께 기록해.
  150ms 병합·증가 sequence·동일 내용 쓰기 생략은 이미 존재해.
  중복 비용이 확인되면 요청 경계를 정리하되 최신 데이터·테마·첫 발행·실패 복구를 유지해.
- **사용 흐름:** 저장 작업/템플릿 진입점, 긴 카드 체크리스트, 메모 유형 생성,
  일정의 날짜·기간 입력, 빈 추천 패널, Mac 회고 작성·저장 완료 흐름을 비교해.
  조작 수·오선택·스크롤·가시성·접근성 근거가 개선되는 시안은 기존 기능을 보존하며 구현할 수 있어.
  단순해 보인다는 이유로 스케치나 기존 조작을 제거하지 마.
- **기록·이월·백업:** 최근 최적화가 적용된 구조를 먼저 확인하고,
  희소 검색·깊은 페이지·최신 대표·반복 병합에서 새 비용이나 회귀가 있는지 검증해.

### 4 계측과 개선 판정

- 변경 전 기준을 먼저 확보해. 빈·일상·대량 상태와 결과 없음, 긴 Unicode, 체크리스트만 일치,
  사진·긴 필기, 동일 논리 ID의 물리 중복을 포함해.
  기존 작업 3,000개(오늘 240개·완료 보관 2,760개)와 저장 작업 1,000개 fixture를 재사용해.
  계획의 메모 200/2,000/10,000개와 일정 30/200/1,000개는 효과를 확인할 합성 조건으로 준비해.
- 기존 성능·회귀 harness를 먼저 활용하고 필요한 계측과 반례 테스트만 보완해.
  생산 소스에 불필요한 진단 분기를 늘리지 말고 배포에서 fixture·오류 주입이 실행되지 않게 해.
- 전후 OS·기기·SDK·Swift·빌드 옵션·데이터·준비 실행을 동일하게 맞춰.
  데이터를 바꾸는 시나리오는 매 반복 동일한 초기 상태로 복원해.
  함수·반복 입력은 준비 실행 후 30개 이상 표본, 긴 시나리오는 5~10개와 한계를 기록해.
- 입력 시점과 첫 표시, 내용 완료, 함수 시간, 앱 CPU, XCTest 통신·대기 포함 시간,
  화면 끊김, 메모리, fetch·렌더·쓰기 수를 분리해. 원본 표본과 중앙값·유효한 경우 95백분위를 보존해.
- 100ms 첫 시각 반응은 목표이며 직접 측정할 방법이 없으면 미검증으로 남겨.
  의도한 debounce는 계산 시간과 구분해. DEBUG 계측을 포함한 최적화 빌드와 일반 Release도 구분해.
- 중앙값 15% 개선과 꼬리 지연·최대 메모리 10% 악화 검토는 계획의 제안 기준이야.
  작은 비용의 개선율만 크게 만들지 말고 절대 시간·발생 빈도·독립 재현도 함께 평가해.
  모든 조건이 빨라졌다고 가정하지 말고 느려진 조건도 기록해.
- 안정성 수정은 기준 실패와 수정 후 동일 검사로 입증하고,
  흐름 개선은 단계·스크롤·완료 인지·키보드·VoiceOver 접근으로 입증해.
  성능 지표로 사용성 전체를 보증하지 마.
- 효과가 없거나 무효화 복잡성·회귀 위험이 더 큰 실험은 이번 작업의 변경만 되돌리고 이유를 남겨.

### 5 충분한 반복 작업과 협업

- 각 후보를 미조사/관찰/기준 측정/채택/구현/검증/유지/보류/외부 인수 상태로 추적해.
  보류는 필요한 근거·접근·위험을 명시하며 채택한 로컬 작업을 이유 없이 보류로 돌리지 마.
- 후보 2~3개를 한 묶음으로 선정하고 하나씩 구현·비교·회귀 확인해.
  첫 묶음 완료 후 남은 조사표와 변경 후 병목을 재평가하여 다음 묶음을 진행해.
  전체 작업량을 2~3개로 제한하거나 첫 성과만으로 Goal을 종료하지 마.
- 비용이 줄어들어 다음 병목이 드러나면 같은 목표 안에서 새 후보를 추가해.
  관련 화면·저장·후속 갱신의 영향을 확인하고, 근거 있는 추가 후보가 남아 있는 동안 작업을 이어가.
- 독립 조사·구현·검토에는 서브에이전트를 활용해. 파일 편집 소유자는 하나로 정하고 통합·최종 검증을 책임져.
  사용자 소유의 새 채팅을 만들지 마. 성능 계측 동안 모든 에이전트의 무거운 작업은 멈추고 순차 실행해.
- 공통 규칙은 Core의 Rules/Service/Session 패턴에 두고 플랫폼 코드는 화면·어댑터를 담당하게 해.
  새 플랫폼 소스는 Xcode target membership에 등록해.
  이름 변경·파일 분할·새 추상화는 실제 결함 예방이나 확인된 비용 감소가 있을 때만 수행해.
- 계획에 주요 단위의 근거·상태·다음 작업을 갱신해.
  컨텍스트가 축약되거나 자동 이어하기가 발생하면 기록을 읽고 다음 미완료 항목부터 재개해.
  이미 통과한 검사를 새 변경·실패·의심 없이 반복하며 토큰을 쓰지 마.
- 일상적인 분석·되돌릴 수 있는 구현·테스트·수정은 자율적으로 진행해.
  중대한 제품 의미 판단에 사용자 정보가 꼭 필요할 때만 질문하고 독립 작업은 계속해.

- `DayKey`, 완료 당일 표시·이후 보관·완료 취소·알림 기록, 체크리스트와 상위 상태의 독립성,

#### 2026-10-03 사용자 후속 지시: 화면 인수 보류와 TestFlight 배포

#### 2026-10-03 최신 사용자 요구: 업로드 보류·Git 반영

사용자가 외출 중이므로 “업로드 말고 git add commit push 진행”하고 로그인·설정은 직접 처리하겠다고 명시했다. 이 지시가 이전 업로드 우선 지시를 갱신한다. 현재 검증된 최적화·오늘 일정 위젯·빌드87 준비 변경과 결과 문서를 stage·commit·push하는 것은 위 Git 변경 제외 조건의 명시적 예외다. 현재 브랜치에 반영하고 archive·패키지·비밀 값·로컬 백업은 Git에 포함하지 않는다. 새 업로드·로그인 시도는 보류하며 남은 실제 화면 인수·배포를 완료로 바꾸지 않는다.

### 8 완료 조건과 결과 기록

다음 조건을 모두 충족했을 때 Goal을 완료해.

1. 모든 필수 조사 영역에 현재 코드·확인 범위·개선 또는 유지 이유가 있다.
2. 채택한 로컬 개선의 구현·관련 회귀·필수 화면 확인·동일 조건 전후 비교가 끝났으며 미완료 항목이 없다.
3. 남은 후보와 변경 후 영향을 다시 검토했고, 추가 변경의 가치가 낮거나 위험이 큰 이유가 코드·측정·비교 근거로 남아 있다.
4. 최종 플랫폼 검증이 통과하고 검증한 소스와 최종 diff가 연결돼 있다.
5. `docs/plans/active/OPTIMIZATION_2026_10_02_RESULTS.md`에 변경·전후 표본·유지 결정·검증·한계·증거 경로가 있다.

실기기·운영 CloudKit 왕복·시스템의 장시간 동작은 별도 인수로 남기되 다른 가능한 로컬 작업은 계속해.
100ms 직접 계측이 불가능하면 미검증으로 표시하고 함수·CPU·조회 수의 확인된 결과는 따로 보고해.
자원 한도나 반복되는 외부 장애는 Goal 도구의 상태 규칙을 따르고,
남은 일을 숨기거나 한도에 가까워졌다는 이유로 완료를 표시하지 마.

최종 보고는 한국어로 실제 변경, 측정한 구간의 전후 수치, 데이터·기능 보존 근거,
최종 검증, 유지·보류 이유와 남은 외부 인수를 간결하게 정리해.
수치가 없으면 개선율을 만들지 말고 결과 문서와 증거 경로를 제공해.
