작성일: 2026-09-17
상태: Goal 구현·격리 화면 검증·최종 플랫폼 게이트 완료. 실기기 출시 전 확인 항목은 별도로 유지한다. 실행 결과와 제한은 [결과 문서](CARRYOVER_AND_REVIEW_DISCOVERY_RESULTS.md)에 기록한다.
기준: `dd2e1d2` 및 작업 트리에 있는 칸반 빈 화면·체크리스트 기본 펼침 변경.

사용자는 보드에서 남은 이월 작업 수와 새로 확인할 작업의 존재를 알아차릴 수 있다.

있으면 활성화하고 둘 다 없으면 제거한다. 할 일 카드에는 시작, 진행 중 카드에는 완료 버튼을
제공한다. 변경으로 두 상태의 남은 작업을 탐색하며, 시스템 수명·시작 제약 안에서 동작한다.

완료 범위는 구현, 관련 테스트, 격리된 앱에서의 화면·동작 확인, 결과 문서 작성까지다.

기존 칸반 변경은 보존한다. 시작 시 현재 diff를 기록하고 다음 파일을 초기 변경과 구분한다.

## 3. 이월함의 동작 계약

### 개수와 새 작업의 의미

- 전체 개수는 현재 이월 대상인 논리 작업 수다. 보드에서 과거·미래 날짜를 보더라도 실제 오늘 기준으로 계산한다.
- 새 작업은 **이 기기에서 마지막으로 확인한 이후 발견한 이월 항목**이다. 기기 간 읽음 상태 동기화는 이번 범위에 넣지 않는다.
- 항목 식별은 논리 `task.id`와 `plannedDayKey`를 사용한다. 물리 `instanceID` 교체나 제목 수정만으로 새 작업이 되지 않는다.
- 오늘로 가져온 작업이 다음 날 다시 미완료가 되면 새 계획일의 이월 항목으로 표시한다.
- 완료/삭제/미래로 이동한 작업은 즉시 현재 개수에서 빠진다. 실패한 저장은 성공으로 집계하지 않는다.
- 같은 항목을 열어본 뒤 단순 새로고침·재실행·중복 수렴·시간대 왕복만으로 새 표시를 다시 붙이지 않는다.
- 다른 기기에서 뒤늦게 들어온 과거 작업도 이 기기에서 아직 확인하지 않은 항목이면 새 작업이다. 실제 발생 시각을 추정하여 표시하지 않는다.

### 최초 실행과 확인 처리

- 기능 도입 후 최초의 성공한 로컬 조회 결과는 기준 목록으로 저장한다. 기존 작업은 전체 개수로 보이고 한꺼번에 새 작업으로 강조하지 않는다.
- 최초 조회 중의 임시 빈 배열이나 조회 실패를 기준 목록으로 저장하지 않는다. 로컬 조회 이후 도착한 동기화 항목은 새 작업으로 처리한다.
- 이월함이 정상적으로 열려 목록이 표시되면 그 목록의 항목을 확인 처리한다. 버튼을 누른 시점이나 조회 실패 시점에는 확인 처리하지 않는다.
- 열 당시의 새 항목 집합을 화면 세션에 보존해 `새 작업 2개`와 우선 정렬이 즉시 사라지지 않도록 한다. 다음에 열면 기존 작업으로 표시한다.
- 열려 있는 동안 들어온 항목도 성공적으로 갱신되어 목록에 포함된 뒤 확인 처리한다. 아직 표시하지 못한 항목까지 일괄 확인하지 않는다.
- 확인 처리는 로컬 UI 상태만 바꾸며 Task를 이동·완료하거나 `updatedAt`을 수정하지 않는다.

### 화면 구성

| 상태 | 보드 진입 버튼 | 이월함 내부 |
|---|---|---|
| 0개 | 아이콘/기존 레이블, 숫자·강조점 없음 | 기존 빈 상태 유지 |
| 기존 5개 | 전체 개수 `5` | `전체 5개` |
| 전체 5개 중 새 항목 2개 | 전체 개수 `5` + 작은 강조점 | `전체 5개 · 새 작업 2개`, 새 작업 먼저 |
| 열어 확인한 이후 | 개수 `5` 유지, 새 강조 해제 | 원래 날짜와 기존 처리 동작 유지 |

- iPhone·좁은 iPad: `tray` 옆에 읽을 수 있는 숫자 배지를 둔다. 새 표시가 숫자나 회고 버튼을 덮지 않도록 버튼 안에 공간을 확보한다.
- 넓은 iPad·Mac: 기존 툴바 흐름 안에서 `이월함 5` 형태를 활용한다. 크기 분기는 기기 이름보다 사용 가능한 폭을 따른다.
- 세 자리 이상에서 공간이 부족하면 `99+`로 줄일 수 있지만, 접근성 설명과 이월함 내부에는 정확한 수를 제공한다.
- 새 표시는 `AppTheme.accent`와 적절한 대비의 배경을 사용한다. 경고 빨강·반복 점멸을 사용하지 않는다.
- 접근성 이름 예: `이월함, 전체 5개, 새 작업 2개`. 색상만으로 정보를 전달하지 않는다.
- 새 작업 묶음 다음에 기존 작업을 두고, 각 묶음 안에서는 기존 계획일·순서 정렬을 유지한다. 항목에는 원래 날짜를 표시한다.
- 기존 오늘로 이동, 원래 날짜에서 완료, 전체 처리, 삭제, 알림 보존 경고 및 처리 결과 안내를 유지한다.

### 날짜 변경 안내

보드 상단의 기존 날짜/입력 영역 아래에 짧은 안내를 배치한다.

> 이월함에 새 작업 2개가 있어요.  [확인] [닫기]

- 새로 발견한 미확인 항목이 있을 때만 보여준다. 같은 날 보드를 오갈 때 반복해서 나타나지 않게 한다.
- 이미 안내한 항목 때문에 다음 날 다시 안내하지 않는다. 같은 날 추가 도착한 항목은 배지에 반영하고, 안내 반복은 하루 한 번으로 제한한다.
- `확인`은 이월함을 연다. `닫기`는 안내만 닫고 새 작업 강조는 유지한다.
- 기존 성공/실패 토스트와 겹치지 않도록 안내 우선순위를 정한다. 작업 처리 오류가 가려지지 않아야 한다.
- 첫 도입 기준 목록에는 안내를 띄우지 않는다. OS 알림이나 앱 아이콘 배지는 추가하지 않는다.

### 구현 위치

공통 코어에 `CarryoverInboxRules`와 로컬 확인 상태 저장소/세션을 둔다. 이름은 구현 시 인접 패턴에 맞게 조정할 수 있다.
날짜·논리 항목 키·새 항목 판정·정렬·개수는 순수 규칙으로, 조회 및 로컬 저장은 별도 책임으로 둔다.
로컬 저장은 주입 가능한 UserDefaults 등의 기존 방식으로 구현하고 UI 테스트용 저장 영역을 분리한다.
Task 본문·제목을 읽음 상태 저장소에 복사하지 않는다.

기존 bounded 이월 조회와 대표 레코드 선택 규칙을 재사용한다. `TaskRules.carryoverTasks`는 그 자체로
논리 ID 중복 제거를 하지 않으므로 기존 대표 선정 규칙과 연결하여 숫자·행·동작 대상이 일치하게 한다.
저장된 확인 키를 임의 개수 제한으로 제거하여 오래된 항목을 새 항목으로 되살리지 않는다.
로컬 상태가 손상되면 앱 데이터는 보존하고 기준 목록 초기화로 복구한다.

양 앱 루트에서 실제 오늘 기준을 보드에 명시적으로 전달하거나 전용 조회 세션을 갱신한다.
과거 보드를 보고 있을 때도 자정/앱 활성화/시간대 변경 후 이월 조회가 갱신되어야 한다.
보드 전체를 매번 재생성해 빠른 입력 초안·포커스·체크리스트 펼침 상태를 잃는 구현은 피한다.

주요 연결 파일: `BoardView`, `DesktopBoardSheets`, `MobileBoardView`, `MobileCarryoverSheet`,
`AppRootView`, `MobileAppRootView`, `TaskRules`, `BoundedQueryService`.

## 4. 작성한 회고 탭의 동작 계약

### 탐색과 상태

- 최상위 네 탭은 유지하고, 기록 화면 안에 `활동 기록 / 회고` 선택기를 둔다.
- 첫 진입은 활동 기록이다. 같은 앱 세션에서 기록을 나갔다 돌아오면 선택한 내부 탭과 탐색 위치를 유지한다.
- 회고 탭은 최초 `전체 기간`, 검색어 없음으로 시작한다. 두 탭의 검색어·기간·스크롤·페이지 깊이·상세 선택을 독립적으로 보존한다.
- 기존 활동 기록의 하루 활동/완료 이력·날짜 기준·히트맵·날짜 탐색을 유지한다.
- 회고 탭에는 작업 날짜 기준, 활동 개수, 완료 통계와 히트맵을 표시하지 않는다. 기간과 회고 검색만 제공한다.
- 회고 탭에서 필터 초기화를 눌러도 회고 탭에 머문다. 기존 `ArchiveFilter.reset()`이 전체/활동으로 바꾸는 부분을 그대로 연결하지 않는다.
- 회고 카드의 `이날 활동 보기`는 해당 날짜의 기존 하루 기록 상세를 연다. 돌아오면 회고의 검색·목록 위치를 유지한다.

### 포함 기준과 정렬

- 제목·본문·기분·날씨 중 하나라도 내용이 있거나, 활성 첨부/레거시 이미지/내용 있는 DiaryBlock이 있으면 포함한다.
- 기분·날씨만 저장한 기존 회고도 포함한다. 이는 기존 `DailyReviewRules.hasContent` 계약을 보존하는 결정이다.
- 아무 내용 없는 DailyReview, 취소한 초안, 작업만 존재하는 날짜, 자동 작업 요약은 포함하지 않는다.
- 다른 기기에서 작성하거나 백업에서 가져온 기존 회고도 포함한다. 현재 모델에 작성 출처 필드는 없으므로 새 출처 판정 필드를 만들지 않는다.
- 기본 정렬은 회고 대상일 `dayKey` 내림차순이다. 과거 회고를 수정해도 작성일 순서를 바꾸지 않는다.
- 날짜별 활성 대표 회고를 기존 수렴 우선순위로 정한 뒤 내용 여부를 판정한다. 최신 대표가 비어 있는데 오래된 중복의 본문을 되살리지 않는다.
- 사진 로딩 실패만으로 카드가 목록에서 사라지지 않게 한다. 기존 이미지 실패/대체 표현을 재사용한다.
- 검색은 회고 제목·본문·기분·날씨와 내용으로 사용하는 레거시 텍스트를 대상으로 한다. 같은 날짜의 Task 제목 때문에 회고가 검색되는 일은 없어야 한다.

### 회고 카드와 상세

표시 순서는 날짜 → 제목 → 본문 미리보기 → 사진 → 기분/날씨 보조 정보다.

- 제목이 없으면 `이날의 회고`를 사용한다. 본문이 없으면 큰 빈 본문 공간을 만들지 않는다.
- 일반 글자에서 본문은 약 3~4줄을 미리 보여준다. 카드 선택으로 전체 회고를 읽는다.
- 목록의 사진은 기존 비동기 썸네일 경로를 사용해 작은 미리보기와 추가 사진 수로 표현한다. 목록에서 원본 전체 이미지를 디코드하지 않는다.
- 전체 읽기 화면에 `수정`과 `이날 활동 보기`를 제공한다. 회고를 읽기 위해 작업 목록을 먼저 펼칠 필요가 없어야 한다.
- `회고 작성`은 오늘을 기본 날짜로 기존 작성기를 연다. 날짜 변경, 기존 회고 불러오기, 저장/취소/미저장 변경 확인은 기존 흐름을 재사용한다.
- 작성·수정 성공 후 해당 카드가 갱신되고, 내용을 모두 지운 회고는 목록에서 빠진다. 실패하면 초안과 기존 목록을 보존한다.
- 회고가 없으면 `아직 작성한 회고가 없어요`와 `회고 작성`을 표시한다. 검색 결과가 없을 때는 별도의 검색 빈 상태와 필터 해제를 제공한다.

### 조회와 코드 구성

`ArchiveScreenState`에 내부 탭 상태와 회고 탐색 상태를 추가한다. 기존 활동 조회 세션은 유지하고,
회고 전용 `ReviewQueryRules`/`ReviewQuerySession` 및 필요한 bounded descriptor를 추가하는 방향을 우선한다.
기존 회고·첨부·블록 조회와 `DiaryAttachmentIndex`, 날짜/검색 규칙을 재사용하며 비즈니스 규칙을 양 플랫폼에 복제하지 않는다.

회고 목록을 위해 `DailyActivityQueryService`의 진행 이력 인덱스나 Task·Focus 전체 기록을 읽지 않는다.
페이지는 날짜 범위와 커서 또는 동등한 bounded 방식으로 읽으며, 희소한 회고가 수년 떨어져 있어도
전체 날짜를 메인 스레드에서 연속 탐색하여 화면을 멈추지 않게 한다.
회고가 비어 있는 원시 페이지를 건너뛰더라도 커서를 전진시키고, 중복 날짜와 다음 페이지 경계 누락을 방지한다.
빠른 검색 변경·탭 이동·동기화 갱신에서는 기존 세션의 취소·세대 검사·페이지 깊이 보존 패턴을 따른다.

일반 목록과 상세는 같은 내용 판정·대표 선정·미리보기 규칙을 사용한다. 레거시 블록을 읽어
미리보기를 구성하는 것만으로 저장이나 마이그레이션을 수행하지 않는다.
기존 작성기와 `DailyReviewService`/`DiaryAttachmentService`의 저장 경계를 유지한다.

주요 연결 파일: `ArchiveScreenState`, `ArchiveQueryRules`, `ArchiveQuerySession`,
`BoundedQueryService+Archive`, `DailyReviewRules`, `DiaryAttachmentService`,
`ArchiveView`, `ArchiveControls`, `ArchiveDayGroupView`, `MobileArchiveView`,
`MobileArchiveFilterSheet`, `MobileArchiveRecordCard`, 양 플랫폼 회고 작성기.

## 5. PlanBase 디자인 기준

- 색은 `AppTheme.background/panel/border/primaryText/secondaryText/accent`와 기존 버튼 스타일을 사용한다.
- 기록 내부 선택기는 목록 상단에서 쉽게 찾을 수 있게 두고, 앱의 최상위 탭처럼 보이는 별도 플로팅 바를 만들지 않는다.
- iPhone에서는 기존 목록 여백과 카드 밀도를 따른다. iPad는 현재 목록/상세 분할에 회고를 연결하고 좁은 창에서는 단일 탐색으로 전환한다.
- Mac은 기존 기록 콘텐츠 폭과 툴바 형태를 유지한다. 최소 창 폭에서 버튼·배지·검색·탭이 서로 밀어내지 않는지 확인한다.
- 모바일 최소 조작 영역 44pt, Mac은 `PlanBaseControlMetrics`의 32pt 이상을 따른다. 숫자 배지가 독립된 작은 클릭 대상이 되지 않게 한다.
- 큰 글자에서는 `planBaseAdaptiveSegmentedPicker()` 등 기존 적응형 정책을 사용한다. 탭·필터·날짜·긴 회고 제목을 고정 높이로 자르지 않는다.
- VoiceOver의 선택 상태·전체 수·새 작업 수, Mac 키보드 포커스·Escape, 동작 줄이기를 확인한다.
- 기본 밝은/어두운 테마와 대비가 까다로운 테마에서 신규 요소를 확인하고, 사용 중인 전체 테마의 토큰 대비를 점검한다.

### 공통 규칙·세션

영속 저장소와 로컬 확인 상태 영역으로 수행한다. Mac은 테스트 인수가 고정된 격리 앱을 사용해

이번 기능의 갱신을 검증하며, 이는 실제 기기 간 CloudKit 검증과 구분하여 기록한다.

관련 공통 테스트와 UI 시나리오를 먼저 실행한다. 이 작업은 공통 API·세션 및 플랫폼 UI를

Debug/Release 빌드와 내장 번들 검증을 확인한다. 새 플랫폼 소스의 Xcode target membership도 확인한다.
검증 통과 뒤에는 새 변경·실패·미해결 우려가 있을 때만 필요한 검사를 반복한다.

## 8. 데이터와 변경 경계

- `AGENTS.md`의 iCloud Drive 금지 경로는 읽기·검색·쓰기를 포함하여 접근하지 않는다.
- `.local/backups/`와 실제 사용자 저장소를 변경하지 않는다.
- V11 및 이전 배포 스키마, 호환 bundle ID/CloudKit/App Group, 백업 형식을 바꾸지 않는다.
- 로컬 읽음 상태 때문에 CloudKit 모델 필드를 추가하지 않는다. 저장 동작은 기존 `PersistenceCommandService` 경계를 유지한다.
- 새 플랫폼 파일은 Xcode 타겟에 등록한다. 공통 규칙은 `shared/Core`에 두고 플랫폼 파일에 복제하지 않는다.
- 범위 밖의 리팩터링·추가 기능·자동 알림을 끼워 넣지 않는다. 정확성에 필요한 인접 수정은 이유와 회귀 검증을 남긴다.

## 9. Goal 완료 조건

1. 이월함·회고 기능이 iPhone·iPad·Mac에서 위 동작 계약을 충족하고, 잠금 화면 추가 요청이 해당 지원 화면에서 충족된다.
2. 새 작업과 작성한 회고의 포함/제외 규칙이 공통 코드와 의미 있는 테스트로 검증된다.
3. 실제 렌더링에서 핵심 흐름, 좁은 화면·큰 글자·테마·접근성을 확인하고 발견한 결함을 해결한다.
4. 기존 칸반 변경과 기록·회고 저장·이월 작업 처리의 회귀가 없다.
5. 필요한 테스트와 최종 빌드 게이트가 통과하고, 결과·스크린샷·소스 기준이 결과 문서에 연결된다.
6. 필수 검증의 미실행/실패가 남아 있으면 완료로 포장하지 않는다. 진행 가능한 작업을 끝내고 남은 원인을 정확히 기록한다.
