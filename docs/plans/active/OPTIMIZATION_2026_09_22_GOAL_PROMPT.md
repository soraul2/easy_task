2026-09-22 현재 코드 `e93d791` 및 이전 최적화·build 80 결과 문서를 분석해 작성했다.
이 문서를 작성하는 단계에서는 Goal을 시작하거나 앱 코드를 수정하지 않았다.
아래 본문을 실행 요청으로 사용한다. 실행 시점의 작업 트리를 다시 확인한다.

---

PlanBase의 현재 기능을 유지하면서 반응성, 대용량 데이터 처리, 저장 안전성,
플랫폼 간 동작 일관성을 개선하는 작업을 하나의 Goal로 설정하고,
분석 → 기준 측정 → 구현 → 재측정 → 회귀 검증 → 결과 정리까지 수행해줘.

오늘 충분한 시간과 토큰을 사용할 의향이 있다. 주요 기능을 폭넓게 조사하고,
근거 있는 개선과 반례 검증에 충분한 작업량을 투입해.
첫 개선 몇 개나 계획 작성만으로 종료하지 말고 아래 조사 범위와 완료 조건을 충족해.
지정하지 않은 숫자를 토큰 예산으로 임의 설정하지 마.
실행 환경과 계정의 실제 한도는 준수하고, 추가 조사 가치가 소진되면 그 근거를 남겨.

2. 조사 범위와 우선순위

기능별로 진입점 → 조회 → 계산 → 화면 갱신 → 저장 → 후속 알림/위젯 갱신을 추적해.
아래 영역 모두에 대해 확인한 코드, 재현 조건, 테스트, 개선 또는 유지 이유를 남겨.

- 앱 시작·복귀·탭 이동, 무결성 수렴, CloudKit import 후 로컬 처리.
- 칸반 추가·상태 변경·완료 취소·체크리스트·이월함과 날짜 이동.
- 저장한 작업·빠른 입력어·루틴 검색·편집·여러 날짜 적용.
- 캘린더 월 이동·기간 일정·날짜 상세·일정 재사용·템플릿 적용.
- 활동 기록·직접 작성한 회고 탐색·검색·기간 필터·페이지와 위치 복원·첨부 이미지.
- 메모의 텍스트·체크리스트·필기, 자동 저장·실패 복구·긴 내용·목록 검색.
- 집중 시작·일시정지·재개·복원·종료, 알림·Live Activity·deep link·App Intent.
- iPhone·iPad·macOS 위젯, Watch 앱과 컴플리케이션.
- 백업 내보내기·비파괴 병합·실패 rollback과 호환성.

우선순위는 데이터 손실/잘못된 동작 → 빈번한 입력과 화면의 지연 → 데이터 증가에 따른
CPU·메모리·조회 비용 → 반복 갱신·파일 쓰기·배터리 비용 → 유지보수 순서로 정해.
발생 빈도, 재현 가능성, 예상 효과, 변경 위험을 함께 평가해.
발견 사항을 확정 결함, 성능 가설, 이미 해결됨, 현재 설계 유지로 구분해.

3. 현재 코드에서 우선 확인할 구체적인 후보

아래는 정적 분석에서 찾은 출발점이다. 실제 병목이나 회귀라고 단정하지 말고
실행 시점의 코드와 측정으로 채택 여부를 결정해.

- 양 플랫폼 보드의 미사용 전체 조회: `desktop/App/Features/Board/BoardView.swift`와
  `mobile/App/Features/Board/MobileBoardView.swift`에는 `templates`, `templateItems`
  `@Query`가 선언되어 있지만 현재 파일에서 값을 사용하는 곳이 확인되지 않았다.
  템플릿 sheet와 빠른 입력이 자체 데이터 경로를 사용하는지 다시 확인하고,
  불필요한 관찰·fetch·화면 재계산을 제거할 수 있는지 검증해.
- 루틴 목록 행 생성: `shared/Core/Components/TemplateLibraryView.swift`는
  `visibleTemplates`를 여러 번 참조하고, `routineRow`마다
  `TemplateService.drafts(from:items:)`로 전체 항목을 필터·정렬·변환한다.
  목록 검색 계산은 9월 14일에 이미 최적화됐다. 이번에는 화면 구성과 행별 반복 계산을

  장기 캐시가 필요하다면 편집·삭제·동기화·즐겨찾기·순서 변경의 무효화 조건을 명시해.
- 빠른 입력 첫 진입과 갱신: `SavedTaskQuickEntryController`, `SavedTaskLibraryService`,
  양쪽 보드의 CloudKit 이벤트 수신을 확인해. `load`는 256개씩 읽지만 결과적으로
  전체 활성 템플릿과 항목을 동기적으로 모은다. 배치 크기가 있다는 이유만으로
  총 작업량이 제한됐다고 판단하지 마. import 이외 이벤트에서도 재조회하는지 측정해.
  실행 직전 재조회로 삭제·변경된 입력어의 오실행을 막는 의미는 유지해.
- 이월함·회고의 신규 경로: `CarryoverInboxSession`의 후보 조회와 ID별 대표 재조회,

  `ReviewDiscoveryRules.records`의 회고별 block 필터링을 조사해.
  데이터가 많거나 희소한 경우, 결과 없음 검색, 페이지를 많이 펼친 뒤 갱신을 측정해.

  `shared/WidgetSupport/CalendarWidgetSnapshotPublisher.swift`의 관찰·저장 알림 갱신,

  실제 fetch·인코딩·쓰기·timeline reload 횟수를 측정해.
  첫 실행·import·날짜/시간대·테마 변경과 앱 복귀의 최신성은 보존해.
- 장기간 기록·메모·시작 무결성: 기존 bounded query, 취소, 페이지 보존,

- 성능 개선은 측정된 비용 감소와 같은 결과·동작을 함께 입증해.
  안정성 개선은 실패 재현과 수정 후 회귀 검사로 입증해.
  효과가 없거나 복잡성과 위험이 더 큰 실험은 이번 작업의 변경만 되돌리고 이유를 남겨.

6. 구현과 병렬 작업 방식

- 의존성이 분리되는 조사·구현·검토에는 서브에이전트를 사용해도 좋다.
  현재 작업 안에서 코어/조회, 플랫폼 UI, 위젯·알림·Watch 등 구체적 범위를 나눠.
  같은 파일의 편집 소유자를 하나로 정하고 주 에이전트가 통합과 최종 검증을 책임져.
  사용자 소유의 새 작업을 별도로 만들지 마.
- 결과를 전달할 때 파일·함수, 재현 근거, 변경 내용, 검증, 남은 위험을 포함해.
  성능 계측은 모든 에이전트의 무거운 작업을 중지한 상태에서 순차 실행해.
- 공통 규칙은 `shared/Core/Services`의 Rules/Service/Session 패턴을 따르고,
  UI 파일에는 플랫폼 표현과 상태 연결을 둬.
  플랫폼 소스 파일을 추가하면 Xcode target membership도 갱신해.
- 작은 검증 가능한 단위로 구현해. 의미 없는 파일 분할·이름 변경·추상화 확대는 피하고,
  큰 UI/테스트 파일은 실제 결함 예방이나 검증 비용 감소가 입증되는 범위에서 정리해.
- 일상적인 구현·테스트·수정 판단은 자율적으로 진행해.
  중대한 제품 의미 변경이나 데이터 안전 판단에 필요한 정보만 확인하고,
  답변을 기다리는 동안 독립적인 작업을 계속해.
  커밋·push·PR 생성·버전 증가·TestFlight 업로드·배포는 이번 범위에 포함하지 마.

7. 검증

- 변경 경로에 관련된 기존 테스트부터 실행해.
  실제 오류, 알고리즘 동등성, 취소/최신 요청, rollback, 중복 수렴을 검증하는 테스트를 추가해.
  단순한 코드 삭제나 문구 변경을 그대로 복제하는 테스트는 만들지 마.
- 기능에 맞게 빈 데이터, 큰 데이터, 검색 불일치, 한글 조합/분해 입력,
  동일 논리 ID의 물리 중복, 삭제·편집 직후 동작, import 이벤트 연속 발생,
  자정·시간대 변화, 백그라운드 복귀, 저장·조회 실패와 재시도를 확인해.
- 최종 코드에서 `./scripts/verify-platform-builds.sh`를 통과시켜.
  이는 공통 Debug/Release 테스트, iOS/macOS Debug/Release 빌드와
  내장 Watch·위젯 번들 검증을 수행하지만 화면 테스트 통과를 의미하지 않는다.
  Watch 변경은 독립 `PlanBase-watchOS` scheme의 Debug/Release도 확인해.
- iOS 연동 변경은 `PlanBaseMobileTests`의 관련 테스트를 별도로 실행해.
  알림, 위젯 발행 순서, Live Activity payload, 모바일 백업 테스트는
  `swift test`만으로 실행되지 않는다는 점을 반영해.
- UI 변경은 `PlanBaseLaunchUITests`의 해당 시나리오와 실제 렌더링을 확인해.
  iPhone·iPad의 좁은/넓은 화면과 큰 글자, macOS의 해당 흐름을 점검하고,
  이미지·위젯·Focus 변경이면 해당 표시 영역도 확인해.
  `PlanBaseResponsivenessTests`는 성능 계측으로 별도 실행하며
  iPhone 하단 탭을 가정한 helper를 iPad에 그대로 적용하지 마.
- 최종 통과 이후 코드를 변경했으면 영향받는 검증을 다시 실행해.
  성공·실패·건너뜀·미실행을 구분하고 원래 실패 로그도 보존해.
  실기기·Apple 계정·실제 CloudKit 왕복·OS 알림 전달·시스템의 장시간 Activity 수명은
  별도 인수 항목으로 기록해. 이번 Goal에서 운영 CloudKit에 접속하지 마.

8. 지속 작업과 완료 조건

- 계획 문서에 기능별 조사표와 우선순위 작업 목록을 만들고,
  각 항목을 미확인/재현·측정 중/구현/검증/유지 결정/외부 인수로 추적해.
  주요 단위가 끝날 때 근거와 다음 작업을 갱신해.
  컨텍스트가 축약되거나 자동 이어하기가 발생하면 기록을 읽고 다음 미완료 항목부터 재개해.
- 첫 수정 후에도 조사표의 나머지 영역과 변경 후 영향을 확인해.
  남은 후보의 효과가 낮다는 결론은 코드·측정 근거로 설명해.
  이미 통과한 검사를 새 변경이나 의심 없이 계속 반복하지 마.
- 이번 Goal의 필수 완료 범위는 전체 조사, 근거에 따라 채택한 개선의 구현,
  로컬에서 가능한 관련 회귀/화면 검증, 변경 전후 비교, 최종 보고다.
  채택한 항목을 미뤄 놓고 근거 없이 범위를 축소해 완료 처리하지 마.
  로컬 필수 검증이 실패하거나 미완료이면 완료로 표시하지 마.
- 별도 인수로 정의한 실제 기기·서버 검증의 미실행은 명확히 남기되,
  그것을 수행한 것처럼 주장하거나 로컬 완료와 혼동하지 마.
  외부 장애가 있으면 다른 가능한 작업을 수행하고,
  더 진행할 수 없는 경우 Goal 도구의 상태 전환 규칙에 따라 사실대로 기록해.
  자원 한도에 도달해도 남은 일을 숨기거나 목표를 달성했다고 표시하지 마.
- 최종적으로 모든 조사 영역에 근거 있는 결론이 있고,
  채택한 개선과 필수 검증이 끝났으며 재현 가능한 결과 문서가 준비됐을 때 Goal을 완료해.

최종 보고는 한국어로 간결하게 작성해. 실제 개선, 동일 조건 전후 수치와 측정 범위,
기능·데이터 의미 보존 근거, 검증 결과, 남은 인수 항목, 결과 문서와 증거 경로를 포함해.
수치가 없으면 개선율을 만들지 말고, 원래 있던 개선과 이번 개선을 명확하게 구분해.
