# iPhone Duo 적응형 인터페이스

상태: 일반 적응형 구현·회귀 검증 완료, Duo 전용 검증 환경 대기 (2026-09-16).
전체 goal 완료 또는 출시 승인 문서가 아니다.

## 범위와 공식 지원

시작 시 Git 작업 트리는 깨끗했다. 최소 OS(iOS 18, macOS 26, watchOS 11),
V11 스키마, CloudKit 모델, 백업 형식과 배포 식별자는 변경하지 않았다.
검사에는 격리된 UI fixture를 사용했다. iCloud Drive, `.local/backups/`, 운영
CloudKit에는 접근하지 않았고 업로드·원격 push는 수행하지 않았다.

- 기본 도구: Xcode 26.6 (17F113), Swift 6.3.3, iOS/watchOS 26.5.
- 추가 도구: Xcode 27.0 beta 3 (27A5218g), Swift 6.4.
- 추가 설치: iOS 27.0 (24A434) 런타임과 전용 VoiceOver iPhone 시뮬레이터.
  기본 Xcode 선택과 배포 최소 OS는 그대로다.
- 설치된 두 Xcode에 Duo device type과 iOS 27.1 SDK가 없다.
  두 설치의 SDK·device type을 반복 확인했으며, 사용자 Applications와 Downloads의
  최상위에도 추가 Xcode 앱·설치 파일이 없었다. 금지 경로는 검색하지 않았다.
- Apple Developer의 Applications 다운로드를 실제 브라우저에서 열면 Apple 계정
  로그인으로 이동한다. 다운로드 목록과 27.1 설치 파일은 인증 전 확인할 수 없었다.
  다른 설치 경로 또는 27.1 설치 환경을 사용자에게 요청한 상태다.
- Apple 문서상 화면 끝까지 확장되는 배치와 세로 시스템 바는 iOS 27.1 SDK,
  Duo 시뮬레이터의 접기·펼치기 검사는 Xcode 27.1 Device Hub가 필요하다.
  빌드 SDK를 갱신하는 것과 최소 지원 OS를 올리는 것은 별개의 작업이다.
- 새 ReservedRegion/ArrangementView API를 현재 SDK에서 추측해 구현하지 않았다.
  우선 시스템 탐색 컨테이너와 안전 영역을 사용한다. 부분 접힘에 따른 집중
  타이머·칸반의 추가 배치는 27.1 도구에서 구현·검증할 후속 항목이다.

공식 근거:

- [Prepare your app for iPhone Duo](https://developer.apple.com/videos/play/tech-talks/111461/)
- [Design for iPhone Duo](https://developer.apple.com/videos/play/tech-talks/111466/)
- [Strike a pose with adaptive layouts](https://developer.apple.com/videos/play/tech-talks/111463/)
- [iPad 창 크기 변경](https://support.apple.com/guide/ipad/work-with-multiple-windows-at-once-ipad08c9970c/ipados)

기기 이름 대신 size class, 콘텐츠 가용 폭과 글자 크기로 판단한다. 콘텐츠는
SwiftUI 안전 영역 안에 두며 배경만 확장한다. 시스템 바의 위치를 가정했던
하단 고정 여백을 줄이고 집중 진입 버튼을 각 탭의 safeAreaInset으로 옮겼다.
비대칭 안전 영역과 접힘 영역의 실제 결과는 Duo 환경에서 추가 확인해야 한다.

## 구현과 상태 소유

| 화면 | 좁은 영역 | 넓고 충분한 영역 | 상태 유지 방식 |
|---|---|---|---|
| 칸반 | 선택 상태 목록 | 할 일·진행·완료 3열 | 같은 스크롤/상태별 목록 정체성, 루트의 날짜·빠른 입력·상세 sheet |
| 캘린더 | 월 → 하루 상세 | 월과 하루 상세 | 선택 날짜와 편집 경로 유지, 하루별 bounded query |
| 메모 | 목록 → 편집 | 목록과 편집 | 루트 경로가 편집 세션·텍스트 선택·체크 항목 선택 소유 |
| 기록 | 목록 → 하루 상세 | 목록과 하루 상세 | 기존 검색/필터/session, 별도 하루 session, 루트의 작업/회고 sheet |
| 집중 | 세로 시간·조작 | 시간과 조작을 나란히 | AnyLayout으로 하위 뷰 유지, 기존 타이머 수명주기 사용 |

`MobileAdaptiveSplitView`는 하나의 NavigationSplitView를 유지한다. 큰 글자이거나
최소 열 너비를 확보하지 못하면 단일 탐색으로 접는다. 메모 전환·닫기는 저장 실패
시 중단하여 초안을 유지한다. 열 재부착 시 같은 텍스트/체크 항목의 입력을 복원한다.
체크리스트에서 명시적으로 닫은 키보드는 폭 변경만으로 다시 열지 않는다.

회고 작성 시 iPhone 회전이 멈추는 현상은 변경 전 HEAD에서도 재현했다.
진단 스택에서 상태 표시줄 preference의 AttributeGraph 순환을 확인했고,
회고 시트에 `.statusBarHidden(false)`를 명시한 뒤 회전·저장·재열기가 통과했다.
초안 폐기 보호와 저장 로직은 변경하지 않았다.

작업 상세의 제목·메모 입력란에는 명시적인 접근성 이름을 추가했다. 회전 후에도
메모 값과 키보드 포커스는 남았지만 내용이 있는 입력란의 접근성 이름이 비어 있는
것을 실제 계층에서 확인했다. 이름 보완 후 회전 중 이어쓰기와 저장·재열기를 검증했다.

실제 창 조절 검사는 화면 키보드가 가리는 모서리 손잡이를 사용하기 위해
키보드를 명시적으로 닫았다가 편집기를 다시 탭한다. 키보드를 유지한 이어쓰기는
별도의 동일 뷰 트리 폭 전환 검사에서 확인했다. 초기 창 제스처 실패 영상은
앱 전환기를 열고 있었으므로 앱 상태 유실의 증거로 사용하지 않는다.
기존 저장한 작업 편집기 검사도 실제 좁은 창의 화면과 접근성 계층을 확인했다.

두 앱 배치는 iPadOS 창 메뉴와 Dock을 실제 조작하고, 두 창의 너비·좌표·조작
가능 여부를 함께 검사했다. 테스트의 일반 TextView 탭은 커서를 문서 시작으로
옮길 수 있어, 이어쓰기 검사에서는 기존 문장 아래를 명시적으로 탭한다. 임시
선택 범위 진단으로 창 배치 자체가 커서를 초기화하지 않는 것을 확인했다.
진단 코드와 추측성 앱 변경은 제거했으며, 적응형 구현을 담은 9개 앱 소스의 해시는
기존 회귀 검증 당시와 동일하다. 이후 추가된 변경은 작업 상세 입력란의 접근성 이름과
식별자 3줄이며, 위 별도 iPhone·iPad 검사와 최종 Release 빌드로 확인했다.

칸반은 창 축소·두 앱 배치 후 빠른 입력 이어쓰기, 작업 추가, 진행 상태 변경,
전체 화면 복귀와 중복 작업 없음을 확인했다. 집중은 실행 중 두 앱 배치로 바꿔도
타이머가 실제 경과 시간 범위에서 줄어들며, 일시정지한 값은 전체 화면 복귀와
닫기·재열기 후에도 유지됐다.

일정 편집기는 전용 키보드 닫기 버튼으로 입력 포커스를 해제한 뒤 창을 변경한다.
기록 필터는 일반 글자 크기에서 분할 선택 버튼, 접근성 글자 크기에서 메뉴이므로
각 형태에 맞게 검사했다. 이 테스트 조작 보완 후 일정·기록 시나리오도 통과했다.
다섯 화면의 대표 흐름을 실제 iPad 창 변경과 두 앱 배치에서 확인했으며, 모든
글자 크기·테마·입력 모드의 조합을 실제 두 앱 배치에서 망라한 검사는 아니다.

테스트용 390pt 영역 전환은 `--ui-testing-adaptive-layout`을 지정한 Debug fixture에만
있으며 Release에는 포함되지 않는다. 이것은 Duo 하드웨어 또는 접힘 시뮬레이션이 아니다.

## 접근성 검토

`testCollectPrimaryScreenAccessibilityAuditFindings`는 지적을 모두 저장하는 검사다.
통과 표시는 접근성 준수 판정이 아니다. 원본 지적과 화면은
`iphone-regression-statusbar-attachments/`에 보존했다.

- 자동 검사 지적: 칸반 9개, 캘린더 39개, 기록 4개, 메모 1개.
- 칸반 우선순위·예상 시간의 작은 영역 지적은 동작이 없는 정적 설명에 해당한다.
  실제 편집·상태 변경 버튼과 분리되어 있다.
- 대표 대비 지적을 원본 스크린샷에서 대조했다. 보드 보조 글자 6.84:1,
  오늘 버튼과 캘린더 날짜 16.05:1, 요일 6.89:1로 측정됐다.
  빈 메모의 지적 영역도 대조했고 아이콘 6.72:1, 제목 15.64:1이었다.
  `accessibility-pixel-samples.json`에 픽셀 표본을 저장했다. 기존 테마의
  텍스트 대비 단위 검사도 전체 회귀에 포함되어 통과했다.
- 이 표본 결과만으로 식별자 없는 대비·잘림 지적 전체를 해소한 것으로 표시하지 않는다.
  큰 글자 보드·캘린더 하루 상세·메모 체크리스트·집중·필터 시트는 별도 UI 검사와
  화면 검토를 수행했다. 달력의 짧은 일정 제목은 상세에서 전체 내용에 접근한다.
- `XCUIVoiceOverService`를 쓰는 검사는 Xcode 27/iOS 27에서만 명시적으로 실행한다.
  구형 도구에서의 skip은 통과로 집계하지 않는다. 최종 검사는 앱 실행 전에
  VoiceOver 연결을 새로 시작하고, 실제 발화의 역할까지 구분하여 대상에 도달한다.
  빠른 입력, 캘린더 탭과 일정 추가, 기록 탭과 날짜 찾기, 메모 탭과 새 메모 버튼,
  메모 내용 편집란을 확인했다. 포커스된 탭과 새 메모 버튼의 double-tap 활성화도
  통과했다. 원본 발화는 `ios27-voiceover-final-clean-attachments/`의
  `8C2568AC-7E7F-4580-B665-350977F0FC6C.txt`에 있다.
  이전 명령 연결 오류는 시스템 설정에서도 재현됐고, 검사 제스처·탐색 방향 문제도
  수정했다. 중간 성공 번들 대신 진단 코드를 제거한 최종 번들을 근거로 사용한다.
  이번 결과는 iOS 27 시뮬레이터 검사이며 Duo 접힘 전후 탐색이나 실기기 rotor
  검사까지 수행했다는 의미는 아니다.
- 기록·빈 메모의 원본 화면도 직접 검토했다. 보이는 제목·안내·조작부의 겹침이나
  잘림은 없었다. 기록 검색창의 긴 안내 문구는 큰 글자에서 잘릴 수 있다는
  예측 지적이며, 식별자 없는 대비 지적은 원본 화면만으로 모두 특정하지 못했다.
- 최대 접근성 글자 크기(AX5)에서 밝은·어두운 테마의 보드, 월간 달력, 하루 상세,
  기록 탐색·검색을 직접 검토했다. 달력의 밀도 높은 날짜는 기존 글자 크기 제한을
  사용하고, 큰 글자에서는 일정 표시를 단순화하며 하루 상세에서 내용을 읽을 수 있다.
  기록 필터 줄은 가로 스크롤이다. 가장자리에서 일부 보이는 ‘모두 지우기’를 스크롤로
  완전히 드러낸 뒤 누를 수 있고, 필터를 지워도 검색어가 유지되는 것을 확인했다.
- 작업 상세의 이름 누락은 `ipad-scroll-detail-controls-attachments/`의
  `FFE78BDE-6ED7-401B-9AA5-D0AA64E3335D.txt`에서 확인했다. 이름 보완 후 제목·메모의
  접근성 이름을 명시적으로 검사했다. 이것을 별도 VoiceOver 실기기 검사로 집계하지 않는다.

## 환경이 준비된 뒤 재개할 순서

같은 Xcode 27.1·Duo 환경 부재를 연속 작업에서 반복 확인했다. 현재 환경에서 가능한
구현과 관련 검증을 마친 뒤 goal은 환경 차단 상태로 둔다. 추가 승인을 기다리는 것이
아니며, Xcode 27.1 설치 경로와 Duo runtime 또는 해당 실기기가 필요하다.

1. 제공된 Xcode의 SDK와 Duo device type을 확인하고, 기존 최소 OS를 유지해 빌드한다.
2. Device Hub에서 접기·펼치기·회전·양쪽 화면 분할을 실행한다. 세로 바와 비대칭 안전
   영역에서 헤더·빠른 입력·시트·집중 진입 버튼을 확인한다.
3. 공식 접힘 영역·부분 접힘 API를 실제 SDK에서 확인하고 필요한 배치를 버전 분기와
   대체 동작으로 구현한다. 제공되지 않는 API를 추측해 추가하지 않는다.
4. 다섯 화면의 선택·검색·초안·커서·스크롤·타이머 유지 시나리오를 Duo에서 다시 실행하고,
   해당 기기·자세를 명시한 스크린샷과 결과를 별도로 남긴다.
5. Duo VoiceOver·실기기 접근성 및 남은 자동 검사 지적을 확인한 뒤 완료 여부를 판단한다.
