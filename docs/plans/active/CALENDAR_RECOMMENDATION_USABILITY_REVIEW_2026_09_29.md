# 캘린더 최근 일정 추천 사용성 분석 및 개선안

작성일: 2026-09-29

상태: 승인된 개선안 구현 및 자동 검증 완료. Mac 직접 검증 완료. 미검증 수동 범위는 9절에 명시한다. 영속 스키마 변경 없음.

1~8절은 구현 전 조사 기록이다. 구현 후 동작과 검증 결과는 9절에 별도로 기록한다.

사용자 제보는 “항목을 클릭해도 해당 내용이 들어가지 않는다”는 간접 전달이며,
정확한 입력값·플랫폼·클릭 위치는 확인되지 않았다. 아래에서 실제 재현한 동작과
소스에서 확인한 제한, 실제 화면 검증이 필요한 가설을 구분한다.

## 1. 핵심 판단

가장 유력한 원인은 후보를 선택해도 제목이 채워지지 않는 것이다.
제목 입력란 바로 아래에 완성된 일정 제목이 표시되지만, 공통 적용 규칙은 현재 제목을
그대로 유지하고 각 플랫폼 화면도 제목을 갱신하지 않는다. 기본값과 같은 기간·색상·
메모를 가진 후보라면 모든 입력값이 그대로여서 “눌러도 아무 일도 없다”는 인상을 준다.

이 동작은 기존 설계와 테스트에 포함되어 있다. 개선 시 제품 동작의 기준과 테스트를
함께 바꾸어야 한다. 저장, CloudKit, 위젯 처리를 먼저 변경할 근거는 발견하지 않았다.

## 2. 조사 및 검증 범위

- 공통 추천·적용 규칙, 조회 세션, 최근 일정 descriptor를 읽었다.
- iPhone/iPad 공용 편집기와 Mac 추가·편집 화면, 키보드 처리 코드를 확인했다.
- 기존 추천 단위 테스트와 모바일 추천 UI 테스트의 검증 내용을 확인했다.
- 앞선 조사에서 관련 공통 테스트 5개가 통과했다. 이번 조사에서는 동일 테스트를
  반복 실행하는 대신 추가 사례를 기존 공통 모듈로 검증했다.
- 임시 실행 파일은 직전 빌드된 `EasyTaskCore` 모듈·오브젝트를 링크했다.
  합성 일정과 메모리 저장소만 사용했으며 실제 사용자 데이터와 CloudKit은 사용하지 않았다.
- 임시 실행 파일의 최초 컴파일은 SDK를 명시하지 않아 Command Line Tools SDK와
  Xcode Swift 컴파일러 버전이 맞지 않았다. 기존 SwiftPM 빌드와 같은 Xcode macOS
  SDK를 명시하여 컴파일과 실행을 완료했다. 전역 도구 설정은 변경하지 않았다.
- 이번 조사에서는 실제 앱 화면 조작, VoiceOver, 한글 IME, 클릭 좌표 검증을 실행하지 않았다.

## 3. 확인된 문제와 개선안

### C1. 후보를 선택해도 제목이 입력되지 않음 — 최우선

**근거:** 공통 규칙 및 합성 데이터 재현, 양 플랫폼 적용 코드, 기존 테스트.

- 재현: `공` 입력 → `공장 점검` 후보 선택 → 제목은 여전히 `공`.
- 1일·파랑·메모 없음 후보와 같은 초기값에서는 적용 전후 모든 값이 같았다.
- 원인: `CalendarEventReuseRules.applying`은 `title: draft.title`을 반환한다.
  모바일 및 Mac 두 적용 함수에도 반환된 제목을 화면에 반영하는 코드가 없다.
- 기존 공통 테스트는 제목 유지를 검사하며 모바일 UI 테스트도 `공`을 기대한다.
- 개선: 명시적으로 선택한 후보의 제목을 입력한다. 현재 시작일은 유지하고 후보의
  포함 일수로 종료일을 계산한다. 선택은 초안에만 반영하고 최종 저장은 기존 버튼으로 한다.
- 완료 기준: 추가·편집·복제 진입과 클릭·탭·키보드 선택에서 같은 결과가 나온다.

### C2. 작성 중인 메모가 교체되거나 비워짐 — 최우선

**근거:** 공통 규칙과 합성 데이터 재현. 전용 되돌리기 UI가 없는 것은 소스 확인.

- 재현: 메모를 작성한 상태에서 메모 없는 후보를 선택하면 메모 값이 `nil`이 된다.
  화면은 이를 빈 문자열로 표시한다.
- 원인: 선택 전 초안과 사용자 수정 여부를 구분하지 않고 후보 메모를 항상 대입한다.
- 영향: 아직 저장되지 않은 사용자 입력을 잃을 수 있다. 일정 전체 취소는 다른 입력도
  폐기하므로 추천 적용만 취소하는 대안이 되지 않는다.
- 권장 정책: 빈 메모에는 후보 메모를 채운다. 이미 작성한 메모와 후보 메모가 다르면
  현재 메모를 유지하고 `작성한 메모 유지 · 추천 메모로 바꾸기`를 짧게 제공한다.
  후보에 메모가 없으면 기존 메모를 비우지 않는다.
- 적용 직전 상태를 이용하는 `되돌리기`를 제공한다. 적용 후 사용자가 다시 편집한
  값까지 덮어쓰지 않도록, 적용한 필드의 현재 값이 적용 직후와 같을 때만 복구하거나
  후속 편집 시 해당 복구 동작을 만료시킨다.
- 기간·색상 교체도 적용 안내와 되돌리기 범위에 포함한다.

### C3. 새 입력의 결과가 오기 전 이전 후보를 선택할 수 있음 — 높은 우선순위

**근거:** 조회 세션 직접 재현과 화면 코드.

- 재현: `공` 결과를 표시한 후 `병원`으로 입력을 바꾸면, 200ms 조회 대기 중에도
  `공장 점검` 후보가 남는다. 완료 후 `병원 방문`으로 교체된다.
- 원인: 이전 비동기 요청은 취소하지만 이미 표시한 결과는 즉시 지우지 않는다.
  화면도 `isLoading`에 따른 선택 제한을 하지 않는다.
- 개선: 입력이 바뀌면 기존 후보의 선택을 즉시 무효화한다. 결과와 검색어/요청 세대를
  함께 보관하고 현재 입력과 일치하는 결과만 적용하도록 검사한다.
- 빠르게 연속 입력할 때 목록 높이가 흔들리지 않도록 짧은 대기 공간을 둘 수 있지만,
  현재 입력과 무관한 이전 후보를 활성 버튼으로 유지하지 않는다.
- Mac은 선택을 배열 위치로 보관한다. 대기 중 이전 목록에서 선택한 위치가 새 목록의
  다른 후보로 이어질 여지가 있으므로 후보 ID로 선택을 관리하고 결과 변경 시 검증한다.
  이 Mac 연속 키 조작 사례는 실제 화면에서 추가 재현해야 한다.

### C4. 메모가 다른 후보를 선택 전에 구분하기 어려움 — 높은 우선순위

**근거:** 합성 데이터 재현.

- 같은 제목·기간·색상에 메모만 다른 두 후보가 모두
  `공장 점검 · 1일 · 파랑 · 메모 있음`으로 표시되었다.
- 원인: 중복 판정에는 메모 본문이 들어가지만, 표시 문자열에는 메모 유무만 들어간다.
- 개선: 제목과 보조 정보를 분리하고 메모 앞부분을 짧게 표시한다. 필요한 경우
  마지막 사용 일정의 날짜를 보조 정보로 제공하되 선택할 날짜로 오인되지 않게 한다.
- 긴 제목에서도 기간·색상·메모 정보가 사라지지 않도록 별도 줄을 사용한다.
  접근성 읽기에는 후보 간 차이를 포함한다.

### C5. 색상 미지정과 기본 파랑이 중복 후보로 나타남 — 보통 우선순위

**근거:** 합성 데이터 재현.

- 제목·기간·메모가 같고 색상만 `nil`/`blue`인 후보 2개가 동일한 한 종류의 요약으로 표시되었다.
- 원인: 표시·적용은 둘 다 기본 파랑으로 처리하지만, 중복 키는 `nil`과 `blue`를 다르게 본다.
- 개선: 추천의 중복 판정에는 실제 적용될 색상 값을 사용한다. 원본 데이터·스키마의
  색상 값을 일괄 변경할 필요는 없다.
- 메모 내용이 다른 후보는 합치지 않고 C4의 표시 개선으로 구분한다.

### C6. 검색 범위가 사용자에게 명확하지 않음 — 보통 우선순위

**근거:** 조회·검색 소스, 중간 단어 검색 재현.

- 현재는 최근 수정된 활성 일정 200개 안에서 제목 접두어를 검색하고 최대 5개를 표시한다.
- `공장 점검`을 `점검`으로 찾을 수 없었다. 최근 200개 밖의 일정은 정확한 제목을
  입력해도 후보가 되지 않는다. 일정 날짜가 최근인지 여부와도 무관하다.
- 개선 1단계: 이름을 `최근 일정에서 가져오기`처럼 명확히 하고, 같은 200개 범위 안에서
  `정확 일치 → 접두어 일치 → 포함 일치` 순으로 확장한다. 한 글자 입력의 포함 검색은
  잡음이 많을 수 있으므로 2글자 이상부터 적용하는 방안을 검증한다.
- 오래된 일정 재사용은 실제 수요를 확인한 후 별도 `더 찾아보기`와 제한된 페이지 조회로
  제공한다. 매 입력마다 전체 테이블을 조회하는 방식은 피한다.
- 초성·오타·의미 검색은 이번 불만의 직접 원인으로 확인되지 않았으므로 후속 범위로 둔다.

### C7. 적용 상태와 조회 실패를 충분히 설명하지 않음 — 보통 우선순위

**근거:** 세션과 화면 소스. 실제 저장소 오류 주입은 미실행.

- 조회 실패는 후보를 비우는 것으로 처리하여 결과 없음과 구분되지 않는다.
- 로딩 값은 있지만 화면이 표시하지 않는다.
- 적용 안내는 실제 변경 여부와 관계없이 `기간·색상·메모를 적용했어요`로 고정되어 있다.
- 제목·날짜 이외 필드를 편집해도 목록을 닫는 정책이 없고, 모바일에는 명시적 닫기가 없다.
- 개선: `대기/결과/결과 없음/실패/적용됨/닫힘`을 구분한다. 짧은 정상 조회에는 과한
  로딩 표시를 피하고, 실패 시 추천 영역에 짧은 안내와 재시도를 제공한다.
- 적용 후에는 선택한 제목과 실제 변경사항을 알려준다. 메모를 보존했다면 그 사실을
  함께 알린다. 저장 완료로 오해하지 않도록 `입력했어요`/`적용했어요`를 사용한다.
- 후보 선택·명시적 닫기 후에는 사용자가 제목을 다시 편집할 때 재개한다.

## 4. 실제 화면에서 추가 확인할 가설

아래 항목은 코드 구조에서 확인할 필요가 생긴 위험이며, 재현된 제품 결함으로 단정하지 않는다.

### R1. 후보 행의 빈 공간을 눌렀을 때 반응하지 않는지

- 후보는 plain 버튼이며 행 전체의 클릭 영역을 명시하는 `contentShape`가 없다.
  실제 히트 영역은 SwiftUI·Form·플랫폼 동작의 영향을 받으므로 코드만으로 판단할 수 없다.
- 제보의 다른 가능한 해석은 “글자 대신 행 오른쪽을 누르면 선택되지 않는다”이다.
- 확인: 글자, 오른쪽 여백, 행 상하단을 각각 눌러 같은 적용이 실행되는지 본다.
- 필요 시 행 전체의 hit region과 모바일 최소 44pt 조작 영역을 명시한다.

### R2. Mac 한글 조합·Return·Esc와 추천 조작이 충돌하는지

- 로컬 keyDown 모니터는 제목 포커스와 키 코드만 확인한다. 한글 조합 상태,
  modifier, 이벤트 창/실제 입력 responder를 확인하는 조건이 없다.
- 선택이 없는 Return은 추천 처리에서 소비하지 않고, 추가/저장 버튼에는 기본 동작
  단축키가 있다. 실제 키 처리 경로에서 사용자의 의도와 다른 저장이 되는지 확인해야 한다.
- 확인: 한글 조합 확정, 한자 후보 선택, 방향키, Return, Esc, Cmd/Option 조합,
  다른 입력칸/창으로 포커스 이동을 테스트한다.
- 개선: 조합 중인 입력은 시스템에 우선 전달하고 유효한 후보가 명시적으로 선택된
  경우에만 추천 적용 키를 처리한다. 후보 이동·적용과 최종 저장이 한 번의 키 입력에서
  동시에 실행되지 않도록 검증한다. 간단한 키보드 안내와 선택 접근성 상태도 제공한다.

### R3. 긴 제목·큰 글자·좁은 화면에서 후보 선택이 어려운지

- Mac 후보는 요약 전체를 2줄로 제한하며 편집기는 고정 폭이다. 모바일은 긴 제목을
  줄바꿈하지만 후보 5개와 키보드가 동시에 있을 때의 실제 조작을 확인해야 한다.
- 확인: 긴 한국어 제목, 서로 다른 메모 후보 5개, iPhone 큰 글자, iPad 축소 창,
  Mac 작은 화면에서 후보 차이와 추가/저장 버튼을 읽고 조작할 수 있는지 검증한다.

## 5. 권장하는 선택 동작

| 값/행동 | 권장 정책 |
|---|---|
| 제목 | 선택한 후보의 전체 제목 입력 |
| 시작일 | 사용자가 정한 날짜 유지 |
| 종료일 | 후보의 포함 일수로 계산 |
| 색상 | 후보의 실제 적용 색상 사용 |
| 빈 메모 | 후보 메모 입력 |
| 이미 입력한 다른 메모 | 현재 메모 유지, 후보 메모로 바꾸는 보조 행동 제공 |
| 후보에 메모 없음 | 현재 메모 유지 |
| 적용 후 | 후보 목록 닫기, 적용 내용과 되돌리기 제공 |
| 저장 | 기존 추가/저장 버튼으로 별도 확정 |

예: 시작일 10월 10일, 제목 `공`, 빈 메모에서 `공장 점검 · 3일 · 빨강` 후보를
선택하면 제목은 `공장 점검`, 기간은 10월 10~12일, 색상은 빨강, 메모는 후보 내용이 된다.
기존에 작성한 메모가 있으면 유지 사실과 교체 방법을 명확하게 보여준다.

## 6. 구현 시 함께 처리할 사항

1. **공통 규칙과 세 화면을 함께 변경한다.** 모바일 공용 편집기, Mac 추가,
   Mac 편집 모두 반환된 제목을 화면 상태에 반영해야 한다.
2. **후보 적용으로 제목이 바뀐 경우를 구분한다.** 현재 모든 제목 변경은 조회를
   재시작하고 적용 안내를 지운다. 단순히 제목 대입만 추가하면 방금 닫은 추천이
   다시 열리고 안내가 사라질 수 있다. 사용자 타이핑과 후보 적용을 별도 상태 전이로 처리한다.
3. **선택은 ID와 검색 요청에 연결한다.** 배열 위치만으로 현재 선택을 판단하지 않는다.
   프로젝트의 `SavedTaskQuickEntryController`는 ID 기반 선택과 오류 상태를 가진
   인접 사례지만, 작업 생성과 일정 초안 적용의 의미가 다르므로 동작 전체를 복제하지 않는다.
4. **메모 보존과 되돌리기 규칙을 공통화한다.** 플랫폼별로 다른 덮어쓰기 정책이 생기지 않게 한다.
5. **기존 테스트의 기대값과 문서를 갱신한다.** 제목 유지 기대를 제목 채움으로 바꾸고
   추가된 예외·상태 전이를 검증한다. 원본 일정·연결 작업·저장 실패 초안 보존은 유지한다.

권장 순서는 C1·C2·C3을 먼저 한 변경 묶음으로 다루고, C4·C5의 후보 구분과 C7의
상태 안내를 이어서 적용하는 것이다. C6의 검색 확장은 별도 범위로 검증한다.
R1·R2는 첫 변경 묶음의 UI 검증에 포함하고, 재현되면 함께 수정한다.

영속 모델 변경 없이 공통 Rules/Session과 UI 상태 개선으로 진행할 수 있다.
공통 API를 변경하는 구현 단계에서는 저장소 지침에 따라 관련 테스트 후 전체 플랫폼
회귀 게이트를 수행한다.

## 9. 승인된 개선안 구현 결과 (2026-09-29)

### 최종 동작

- 추천은 전체 제목·포함 일수·실제 표시 색상을 초안에 입력한다. 현재 시작일과
  원본 일정·연결 작업은 유지한다. 최종 저장은 기존 추가/저장 동작을 사용한다.
- 빈 메모에는 추천 메모를 입력한다. 작성한 메모는 앞뒤 공백만 정리하여 비교하며,
  보존하는 원문은 바꾸지 않는다. 서로 다른 추천 메모는 `추천 메모로 바꾸기`로만 교체한다.
- `CalendarEventRecommendationApplication`은 적용 전후 초안과 선택한 후보를 보관한다.
  메모 교체도 같은 적용에 포함하며, 되돌리기는 최초 적용 전 초안으로 한 번 복구한다.
  제목·날짜·색상·메모의 수동 편집이 시작되면 적용 기록과 후속 동작을 만료시킨다.
- 모든 표시 값이 같으면 동일 내용 안내만 표시한다. 실제 변경이 있는 경우에만 되돌리기를 제공한다.
- 최근 수정된 활성 일정 200개 조회·최대 5개 표시는 유지한다. 정확·접두어·포함 일치
  순으로 정렬하고 포함 검색은 정규화된 2글자 이상에만 적용한다. 같은 등급은 기존
  수정 시각/ID 순서를 따른다. 색상 미지정·기본 파랑은 같은 설정으로 중복 제거한다.
- 세션이 로딩·결과·결과 없음·실패·닫힘·적용을 구분한다. 입력 변경 즉시 기존 결과와
  키보드 선택을 비우고 요청 세대와 검색어가 유효한 결과만 표시·적용한다.
  사용자의 제목 편집 Binding만 재검색하므로 추천 적용·되돌리기로 목록이 다시 열리지 않는다.
- 공통 후보 UI는 제목, 기간·색상, 2줄 메모를 분리한다. 전문 펼침은 별도 버튼이고
  한 번에 하나만 펼친다. 버튼 전체 영역과 모바일 최소 44pt, 후보 접근성 이름·선택 상태를 제공한다.
- Mac 본문은 스크롤하고 하단 저장/취소는 고정한다. 실제 입력 responder·창·한글 조합 상태·
  modifier를 확인한 뒤 ↑↓/Return/Esc를 처리한다. 추천에 소비한 Return은 저장으로 전달하지 않는다.
- 조회 실패 안내와 재시도를 추가했다. DEBUG의 `--ui-testing`과 전용 실패 인자를 동시에
  전달한 경우에만 메모리 fixture의 첫 조회 실패를 주입할 수 있다. 운영 데이터 경로에는 적용되지 않는다.

합성 일정과 `--ui-testing` 메모리 저장소만 사용했다. 실제 사용자 저장소·CloudKit은

  추천/200개 조회 테스트 14개 통과. 기존 DST 기간 계산·복제의 원본 및 연결 작업 보존

### 남은 수동 검증 범위

한글 IME의 실제 조합 중 키 입력·한자 후보 선택, VoiceOver 음성 낭독/로터 탐색,
iPad 멀티태스킹 축소 창의 모든 크기, Mac 다른 창으로 이동하는 순간의 키 입력은
직접 검증하지 않았다. iPhone 최대 글자 크기에서 키보드를 계속 연 상태로 모든 보조 동작을 수행하는 흐름은 별도 확인이 필요하다. 접근성 트리·코드 가드 확인을 이들 시나리오의 통과로 간주하지 않는다.
