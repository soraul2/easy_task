# 회고 없이도 보이는 하루 기록 개선 계획

- 작성일: 2026-09-04
- 상태: 구현·로컬 검증·TestFlight build 66 업로드 완료 · 실기기 접근성 확인 별도
- 대상: macOS 및 iPhone·iPad의 기록/보관함
- 최우선 요구: **회고를 쓰지 않아도 날짜별로 어떤 작업을 했는지 바로 알 수 있어야 한다.**

## 1. 목표와 완료 기준

기록 화면을 열면 작업 제목과 그날의 활동이 먼저 보이고, 회고는 그 아래에 사용자가
원할 때 덧붙이는 내용으로 둔다. 회고 작성 여부가 날짜 카드 생성이나 작업 목록 노출의
조건이 되어서는 안 된다.

최종 목표는 다음 세 가지다.

1. 회고가 없는 날에도 완료한 작업 제목을 추가 조작 없이 확인한다.
2. 완료하지 않은 작업도 진행 기록이나 종료된 집중 세션이 있으면 해당 날짜에서 찾는다.
3. 기록 속 작업을 누르면 생성 시각과 활동·소요 시간을 보여주는 읽기 전용 작업 기록을 연다.

1차 개선은 현재 완료 기록을 쉽게 보이게 하는 단계다. **진행만 한 날과 집중만 한 날까지
보여주는 2차 개선이 끝나야 이번 요구의 전체 구현이 완료된 것으로 본다.**

## 2. 현재 상태와 개선 방향

| 현재 확인한 상태 | 사용자에게 생기는 문제 | 개선 방향 |
|---|---|---|
| 회고 없이도 완료 작업으로 날짜 카드가 만들어짐 | 작업 목록이 기본으로 접혀 있어 무엇을 했는지 잘 보이지 않음 | 작업 제목을 기본 노출 |
| 회고 제목·본문·사진이 작업 목록보다 먼저 나옴 | 회고를 쓰는 기능처럼 느껴짐 | 날짜 → 작업 요약·목록 → 회고 순서 |
| 완료 상태의 Task만 보관함 목록에 포함 | 진행했지만 끝내지 못한 날이 빠짐 | 완료 활동·진행 이벤트·집중 기록으로 날짜 구성 |
| 활동 그래프가 상단의 큰 영역을 차지함 | 실제 작업 제목을 보기까지 스크롤이 필요함 | 그래프를 접을 수 있는 보조 영역으로 배치 |
| 작업 행에서 상세를 직접 열 수 없음 | 계획일과 완료일이 다른 작업은 보드 이동 후 찾지 못할 수 있음 | 논리 Task ID로 직접 상세 열기 |
| 화면 재진입·조회 오류 처리가 일부 불완전함 | 갱신이 멈추거나 오류를 기록 없음으로 오해할 수 있음 | 재활성화·상태 유지·오류/재시도 처리 |

현재 기록의 날짜 기준은 완료일과 계획일이며, 계획일 기준도 완료한 작업만 조회한다.
새 활동 기록과 기존 날짜별 완료 내역의 의미를 구분해 유지한다.

## 3. 목표 화면

### 3.1 기본 구성

위에서 아래로 다음 순서를 사용한다.

1. `기록` 제목, 검색, 날짜 선택, 필터
2. 최근 날짜부터 나오는 하루 기록 카드
3. `완료 활동 · N일 연속` 요약은 항상 표시하고, 같은 카드 안의 그래프 영역만 접고 펼친다. 별도 통계 탭과 기간 통계 카드는 제거

날짜 카드 안에서는 작업을 먼저 보여준다. 기본 제목은 날짜로 충분하며, 내용이 없는
`작업 기록` 제목을 반복해 공간을 차지하지 않게 한다.

```text
9월 4일 금요일                         하루 자세히 보기
작업 3개 · 이날 완료 2개

✓ 기획서 마무리          이날 완료 · 진행 상태 40분
✓ 장보기                 이날 완료
▷ 영어 공부              진행 상태 20분 · 집중 15분*

+ 회고 남기기

* 집중 시간은 해당 날짜에 종료한 세션 기준
```

위 숫자는 화면 설명용 예시다. 실제 화면에는 저장된 근거가 있는 정보만 표시한다.
`진행 상태 시간`은 작업을 진행 상태로 둔 구간이며, 실제로 계속 일했다는 뜻으로 표현하지 않는다.

- 작업은 카드마다 기본 3개를 보여준다. 나머지는 `작업 N개 더 보기`로 카드 안에서 펼친다. 날짜를 누르면 하루 상세를 연다.
- 3개 이하인 날에는 목록을 펼치는 버튼이 필요하지 않다.
- 같은 작업에 완료·진행·집중 기록이 있으면 한 행에 함께 표시한다.
- 검색 중에는 일치한 작업을 우선 노출하고, 일치한 메모·체크리스트 일부를 보여준다.
  기본 3개 제한 때문에 검색 결과가 숨겨지지 않게 한다.
- 회고가 있으면 작업 목록 아래에 짧은 미리보기를 둔다. 본문·사진은 펼쳐서 확인한다.
- 회고가 없으면 작은 `회고 남기기` 동작만 제공한다. 미작성 경고나 빈 본문 상자를 두지 않는다.
- 큰 글자 설정에서는 줄바꿈과 카드 높이 증가를 허용한다. 한 화면에 넣기 위해 글자를 줄이지 않는다.

### 3.2 하루 상세와 이동

- 날짜 또는 `하루 자세히 보기`를 누르면 해당 날짜의 전체 작업과 회고를 연다.
- 작업 행을 누르면 논리 Task ID와 선택한 날짜를 전달해 읽기 전용 `작업 기록`을 연다.
  보드의 편집 창을 기본 동작으로 재사용하지 않는다.
- 작업 기록에는 생성 시각, 현재 상태, 선택한 날의 진행·집중 시간, 전체 누적 시간,
  첫 진행·최근 완료 처리 시각과 시작/종료 이력을 보여준다.
- 진행 시간은 닫힌 구간만 합산하고, 집중 시간은 종료한 세션의 실제 집중 시간으로 별도 표시한다.
  현재 체크리스트·작업 메모와 과거 활동을 구분한다. 날짜만 남은 이전 완료 기록에 시각을 만들지 않는다.
- 이력 조회는 해당 Task로 제한하고 256개 단위로 읽으며, 화면은 최근 20개부터 펼친다.
  저장·상태 변경·집중 시작 버튼을 두지 않는다. 작업 변경은 보드에서 수행한다.
- `보드 열기`는 날짜별 계획을 확인하는 보조 동작으로 남긴다. 작업 상세 진입 경로로 사용하지 않는다.
- 상세에서 돌아오면 검색어, 필터, 펼침 상태, 로딩한 페이지와 스크롤 위치를 복원한다.
- 날짜 선택으로 기록이 없는 날을 열 수도 있다. `이 날짜에 저장된 활동 기록이 없어요`라고
  표시한다. 사용자가 아무 일도 하지 않았다고 단정하지 않는다.
- macOS는 넓은 상세 패널/시트, iPhone은 탐색 화면, iPad는 가용 폭에 맞는 상세 배치를 사용한다.
  공통 데이터 의미와 기본 작업 노출 수는 동일하게 유지한다.

### 3.3 날짜 기준·검색·그래프

- 1차 개선에서는 현재 `완료일 기준` 동작을 유지한다. `계획일 기준` 설명은
  `계획일로 묶은 완료 작업`으로 명확히 한다.
- 2차 개선에서는 `하루 활동`을 기본 보기로 추가한다. 기존 완료일/계획일 조회는
  필터의 `완료 작업 모아보기` 아래에서 선택할 수 있게 한다.
- 기존 `TaskHistoryDateBasis`의 의미를 바꾸어 활동일을 끼워 넣지 않는다.
  화면용 보기 상태에서 하루 활동과 기존 완료 작업 조회를 구분한다.
- 검색 대상은 우선 기존 작업 제목·작업 메모·체크리스트·회고를 유지한다.
  독립 메모 기능의 수정일을 작업 활동으로 취급하지 않는다.
- `회고 있는 날만` 필터를 선택한 경우에만 회고 유무로 날짜를 제한한다.
- 히트맵의 칸을 누르면 그 날짜의 하루 상세를 연다. 목록의 검색어나 기간 필터를
  몰래 변경하지 않는다. 하루 상세는 선택한 날짜 전체를 보여준다.
- 기존 스트릭·히트맵의 집계는 **작업 완료 활동**으로 유지하고 이름을 명시한다.
  진행·집중만 있는 날도 하루 기록에는 나올 수 있음을 짧게 설명한다.
- 완료 활동 요약과 펼침 버튼은 하나로 통합한다. 접힌 상태에서도 연속 완료 일수를
  갱신하며, 불러오는 중이나 조회 실패를 `0일 연속`으로 표시하지 않는다.
- 그래프의 펼침 상태를 기억한다. 오늘 안내·최근 1년 최고 기록·범례는 그래프와 함께
  접고 펼치고, 불러오기 실패 안내와 재시도는 접힌 상태에서도 제공한다.
- 통계 탭과 계획 대비 완료율·지연 완료 등의 기간 요약은 제공하지 않는다.
  날짜 카드의 `작업 N개 · 이날 완료 M개`와 작업별 진행·집중 시간은 유지한다.

## 4. 어떤 정보를 하루 기록으로 보여줄 것인가

첫 구현은 기존 V10 데이터로 화면용 기록을 계산한다. 새 회고나 자동 요약 문장을
DB에 생성하지 않고, 조회 결과를 공통 값 타입으로 조합한다.

| 정보 | 근거와 날짜 | 표시 원칙 |
|---|---|---|
| 완료 활동 | `TaskCompletionActivity.activityDayKey` | 저장된 활동일로 `이날 완료` 표시. 현재 작업을 다시 진행 중이어도 과거 완료 사실은 유지 |
| 예전 완료 내역 | 기존 backfill 및 `TaskHistoryDateRules` | 실제 활동일을 확인할 수 없으면 `이전 완료 기록` 표시와 설명 제공 |
| 진행한 작업 | `TaskProgressEvent`의 유효한 시작·종료 구간 또는 시작 사실 | 날짜와 겹치는 확인된 구간만 일별로 표시 |
| 종료된 집중 | `FocusSession.endedAt`, `focusedDurationSeconds` | 종료일에 포함하고 `종료일 기준` 안내 |
| 회고 | `DailyReview.dayKey` | 선택적으로 같은 날짜에 결합. 회고만 있는 날도 유지 |

### 4.1 완료 활동과 과거 데이터

- 실제 완료 버튼을 누른 날, 사용자가 지정한 완료일, 계획일은 서로 다를 수 있다.
  예를 들어 9월 2일 작업을 9월 4일에 완료 처리했다면 캡처된 활동은 9월 4일에,
  지정된 완료일/계획일 조회는 기존 규칙에 맞는 날짜에 표시한다.
- `captured`와 legacy backfill의 근거 수준을 구분한다. 이전 기록으로 복원한 날짜나
  시각을 실제 행동을 관측한 것처럼 표시하지 않는다.
- 완료 활동이 없는 이전 완료 Task도 기존 완료일 해석 규칙으로 찾을 수 있게 한다.
  해당 Task에 정규 활동 기록이 있는지 먼저 확인하고, fallback을 중복 추가하지 않는다.
- 기존 activity 무결성·backfill의 대표 레코드와 날짜 규칙을 사용한다.
  저장된 `activityDayKey`를 현재 시간대로 다시 계산하거나 legacy UTC 규칙을 바꾸지 않는다.
- 하루의 `작업 N개`는 논리 Task ID의 합집합이다. 같은 날 재완료·진행·집중을 반복해도
  작업 수는 한 번만 센다. 완료 수와 집중 세션 수는 서로 다른 단위로 표시한다.

### 4.2 진행 기록과 시간

- 기존 `TaskProgressEventRules`의 중복 제거, 정렬, 시작·종료 짝짓기 규칙을 재사용한다.
- 단독 `stopped` 이벤트는 실제 진행의 증거로 사용하지 않는다. 현재 구현에서는
  미진행 작업의 완료나 완료 취소에서도 발생할 수 있다.
- 확인된 닫힌 구간이 자정을 넘으면 날짜 경계에서 나누어 진행 상태 시간을 계산한다.
  날짜 길이를 24시간으로 고정하지 않고 `DayKey`와 Calendar를 사용한다.
- 범위 밖에서 시작하고 범위 밖에서 끝난 구간도 중간 날짜에 포함해야 한다.
  범위 안의 이벤트만 조회해서 이런 구간을 누락하지 않는다.
- 종료되지 않은 시작은 시작한 날의 `진행 시작` 사실로 표시한다. 시작만 남은 기록을
  근거로 그 뒤 모든 날짜를 일한 날로 채우거나 확정 시간을 만들지 않는다.
- 현재 진행 중인 상태는 현재 작업 상세에서 확인한다. 과거 카드의 `진행 기록`과
  현재 상태를 혼동하지 않게 한다.
- compatibility boundary 등 시간이 불명확한 구간은 `시간 기록 없음`으로 표시한다.
  예정 시간(`estimatedMinutes`)이나 현재 상태로 과거의 시간을 추정하지 않는다.

### 4.3 집중 시간과 남아 있지 않은 정보

- 집중 시간은 중단·완료 등 결과에 관계없이 유효한 종료 세션의 실제 저장 시간으로 계산한다.
  집중 완료 횟수와 세션 횟수는 구분한다.
- 현재 데이터에는 휴식·일시정지의 상세 시점이 없으므로 자정을 넘긴 집중 시간을
  날짜별로 임의 분배하지 않는다. 기존 Focus 계획의 종료일 집계 규칙을 유지한다.
- 실행 중인 기기 로컬 집중 타이머는 종료·저장 전까지 과거 기록 합계에 넣지 않는다.
- 진행 상태 시간과 집중 시간은 겹칠 수 있으므로 합산한 `총 작업 시간`을 만들지 않는다.
- Task 제목은 현재 레코드를 연결해 보여준다. 당시 제목을 고정 보존하는 기능으로 안내하지 않는다.
- Task가 없더라도 남아 있는 완료 활동·집중 기록은 보존하며 `작업 정보를 찾을 수 없음`으로
  표시한다. 동기화 도착 순서 때문에 잠시 없을 수 있어 곧바로 `삭제된 작업`이라고 단정하지 않는다.
- 현재 작업 삭제는 진행 이벤트도 삭제한다. 사라진 진행 이력이나 과거 제목을 이 계획에서
  복원한다고 약속하지 않는다. 삭제 후에도 모든 이력을 보존해야 한다면 후속 스키마 계획으로 다룬다.
- 예정된 일정·미시작 할 일은 실행 증거가 없으므로 활동으로 세지 않는다.

## 5. 공통 코드와 조회 구조

다음 이름은 구현 시 사용할 후보이며, 기존 타입과 책임이 겹치면 합친다.

| 역할 | 작업 위치·후보 |
|---|---|
| 화면에 필요한 하루/작업별 값 타입 | `shared/Core/Models/DailyActivityRecord.swift` |
| 날짜 귀속, 근거 표시, 중복 제거, 일별 구간 계산 | `shared/Core/Services/DailyActivityRules.swift` |
| 범위 조회, 대표 Task 연결, 날짜별 페이지 구성 | `shared/Core/Services/DailyActivityQueryService.swift` |
| 검색 취소, 페이지 유지, 갱신·재활성화·오류 | `shared/Core/Services/DailyActivityQuerySession.swift` |
| 작업 기록 조회·표시 | `shared/Core/Services/TaskRecordQueryService.swift`, `shared/Core/Models/TaskRecord.swift`, `shared/Core/Components/TaskRecordSheet.swift` |
| macOS 목록·상세 연결 | `desktop/App/Features/Archive/ArchiveView.swift`, `ArchiveDayGroupView.swift` |
| iPhone·iPad 목록·상세 연결 | `mobile/App/Features/Archive/MobileArchiveView.swift`, `MobileArchiveRecordCard.swift` |

조회 구조의 요구 사항:

1. 완료 활동·진행 구간·종료 집중·회고·이전 완료 fallback의 날짜 합집합으로 목록을 구성한다.
   완료 Task에서만 날짜를 시작하면 진행/집중만 있는 날이 다시 빠지므로 사용하지 않는다.
2. 날짜 그룹을 분할하지 않는 페이지 단위를 유지한다. 기본 30일 그룹을 상한으로 하고,
   작업이 많은 한 날짜는 제목 미리보기와 요약을 먼저, 나머지는 하루 상세에서 조회한다.
3. Task·체크리스트는 대상 ID를 묶어서 조회하고 사진 원본은 목록에서 읽거나 디코딩하지 않는다.
   작업 행마다 중복 관찰 쿼리를 추가하지 않는다.
4. 진행 구간 조회를 먼저 기술 검증한다. 기존 `events(forTaskIDs:)`는 해당 작업의 전체 이력을
   읽으므로, ID를 묶었다는 이유만으로 날짜 범위 조회가 완성되었다고 간주하지 않는다.
5. 시작/종료가 둘 다 조회 기간 밖에 있는 구간, 중복 시작, 뒤늦은 CloudKit 이벤트를 포함해
   정확성과 비용을 검증한다. 필요하면 원본에서 다시 만들 수 있는 기기 로컬 구간 인덱스를 사용한다.
   인덱스의 초기 구성은 작은 묶음으로 진행하고 변경·백업 병합 때 무효화/재구축한다.
6. 임의의 조회 상한 때문에 오래된 활동을 조용히 누락하지 않는다. 정확한 범위 조회가
   성능 목표를 충족하지 못하면 조회 설계를 보완한 뒤 2차 화면을 출시한다.
7. 큰 스캔은 묶음 사이에 취소·화면 응답 기회를 제공한다. 작업 세대 번호로 오래된 응답을 버린다.
   SwiftData 모델이나 ModelContext를 임의로 다른 actor에 넘기지 않는다.
8. 저장 변경·CloudKit import·화면 복귀·앱 활성화·자정·시간대 변경 시 필요한 범위를 갱신한다.
   화면 이탈로 취소한 session은 복귀 시 다시 활성화한다.
9. 검색 대기 중 갱신 이벤트가 발생해도 이전 검색 조건으로 되돌아가지 않도록
   요청 중인 필터와 적용된 필터를 구분한다. 갱신 후 페이지 깊이와 선택 날짜를 유지한다.
10. 새로고침 실패 시 이전 결과와 오류 안내를 유지한다. 처음 조회 실패와 실제 기록 없음은
    서로 다른 상태로 표시하고 재시도를 제공한다.

영속 모델·호환 식별자·CloudKit schema·백업 형식은 첫 구현에서 변경하지 않는다.
진행 구간 인덱스가 필요해도 재생성 가능한 로컬 캐시로 취급한다. 영속 모델 변경이
불가피해지면 V10을 고치지 않고 V11 이상과 migration·백업 영향 검토를 별도 설계한다.

## 7. 검증과 인수 조건

### 데이터·동작 검증

| 사례 | 기대 결과 |
|---|---|
| 회고 없음 + 완료 작업 3개 | 작업 제목 3개가 처음부터 보임 |
| 회고 없음 + 진행 후 중단한 작업만 있음 | 해당 날짜와 작업이 표시되고 구간 시간이 맞음 |
| 회고 없음 + 종료된 집중 세션만 있음 | 종료일에 작업과 집중 시간이 표시됨 |
| 같은 작업을 같은 날 완료·진행·집중·재완료 | 작업 행/작업 수는 1개, 근거와 세션 수는 정확히 구분 |
| 9/2 계획 작업을 9/4에 완료 처리, 지정 완료일은 9/2 | 실제 캡처 활동은 9/4, 기존 날짜 조회는 9/2, 상세는 같은 Task |
| 완료 후 작업을 다시 진행으로 변경 | 이전 완료 활동은 남고 현재 상태와 구분됨 |
| 오래된 완료 기록에 실제 활동일/시각이 없음 | legacy 표시, 임의 시각이나 진행 시간 없음 |
| 23:50~00:20의 닫힌 진행 구간 | 날짜별 진행 상태 시간이 10분/20분으로 나뉨 |
| 시작과 종료가 모두 조회 범위 밖 | 범위 중간 날짜의 진행 구간도 빠지지 않음 |
| 열린 시작·중복 시작·단독 stopped·compatibility boundary | 가짜 구간이나 이후 날짜의 활동을 생성하지 않음 |
| 자정을 넘긴 집중 세션, 일시정지 포함 | 저장된 집중 시간 전체를 종료일에 표시, 진행 시간과 합산하지 않음 |
| Task보다 활동/집중이 먼저 동기화됨 | 기록 유지, 임시 제목 안내, Task 도착 후 제목 갱신 |
| Task 제목 변경 또는 삭제 | 현재 제목 정책과 남아 있는 근거만 표시, 존재하지 않는 과거 제목 복원 없음 |
| 중복 import·백업 병합 | 대표 레코드 규칙 준수, 일별 작업/시간 중복 없음 |
| 검색 입력 직후 저장 변경, 탭 왕복, 앱 복귀 | 최신 검색 유지, session 갱신 재개, 위치 보존 |
| 목록 조회 실패 | 0개/빈 기록으로 위장하지 않고 오류와 재시도 표시 |
| 회고만 있는 날 또는 선택한 빈 날짜 | 회고는 유지, 빈 날짜는 저장된 활동 없음으로 안내 |

### 화면·성능 검증

- iPhone 기본 글자 크기에서 기록 진입 후 그래프를 지나 스크롤하지 않아도 첫 작업 제목을 확인한다.
- 큰 글자·긴 제목·VoiceOver에서는 정보 순서가 날짜 → 작업 → 회고이고, 의미가 색상에만 의존하지 않는다.
- macOS 키보드 검색과 작업 상세 열기, iPad 좁은 창/가로 화면의 버튼·줄바꿈을 확인한다.
- 로컬 fixture로 최소 1만 Task·10만 진행 이벤트와 희소한 오래된 기록을 확인한다.
  긴 작업 하나에 이벤트가 몰리는 사례와 신규 캐시 구성/뒤늦은 과거 import도 포함한다.
- 성능 목표는 시험 기기와 데이터 조건을 기록한 뒤 판단한다. 목표값은 최근 30일 첫 내용
  1초 이내, 검색/날짜 변경 시 이전 작업이 화면 반응을 막지 않는 것이다. 초기 인덱스 구성은
  진행 상태와 취소를 제공하고 완료 전 수치를 최종 합계처럼 표시하지 않는다.
- 관련 공통 테스트를 먼저 실행하고, 공통 API 및 양 플랫폼 연결이 끝나면
  `./scripts/verify-platform-builds.sh`로 전체 회귀를 확인한다.
- 실제 데이터 검증은 로컬 또는 메모리 저장소에서 한다. 일반 테스트에서 CloudKit에 접근하지 않는다.

공통 테스트는 `ArchiveQuerySessionTests`, `ArchiveReviewRulesTests`, `TaskActivity*Tests`,
`TaskProgressEventTests`, `FocusModeTests` 인접 패턴을 재사용한다. UI 테스트의 기존
`작업 기본 접힘` 기대는 이번 요구의 `기본 제목 노출` 기대에 맞춰 갱신한다.
플랫폼에 새 Swift 파일을 추가하면 Xcode target membership도 등록한다.

## 10. 구현 결과와 검증 기록

2026-09-04에 1·2차 기능과 검색 개선을 구현했다. 이후 사용자 요청에 따라
통계 탭과 기간 요약을 제거하고, 완료 활동 그래프와 날짜별 작업 요약을 유지했다. 상세 검증 결과는
[하루 기록 검증 보고서](ARCHIVE_DAILY_ACTIVITY_VALIDATION.md)를 따른다.
새 영속 스키마나 자동 생성 회고 없이 기존 완료 활동·진행 이벤트·집중 세션으로 조회한다.
iPad의 넓은 화면에는 검색란과 필터를 고정 노출하고, 좁은 화면에서는 기본 검색 UI를 사용한다.
실기기 VoiceOver와 실제 계정의 CloudKit 동기화 검증은 로컬 시뮬레이션 결과와 구분한다.
