## 로컬 캐시·세션 정책

- SwiftData 로컬 원본과 iCloud 동기화는 구분한다. 로컬 조회도 반복 비용이 있으므로 기존 bounded query에 더해 준비한 값을 재사용한다.
- `/입력어`는 같은 context의 깨끗한 library value snapshot과 준비된 alias key를 유지한다. 템플릿 변경·직접 저장·성공 import·명시적 refresh는 캐시를 무효화한다. 2026-10-13 후속 변경은 제출 직전 최신 template/child 대표를 전용 조회로 검증하고, 성공 시 전체 library의 draft 구성·정렬을 생략한다. 잘못된 입력은 저장 명령 전에 거절하고 실패 때 최신 표시 library를 다시 읽는다. 캐시만으로 제출하지 않는다. 일반 제목 입력은 library를 읽지 않는다.
- 이월함은 변경된 logical Task ID만 대표 조회 후 캐시에 병합한다. 오늘 작업 생성·삭제가 이월 결과에 영향을 주지 않으면 전체 재조회와 snapshot 재생성을 생략한다. 범위를 모르는 변경·import·날짜/시간대 변경·foreground는 full fallback을 유지한다.
- 진행 기록은 표시된 Task ID의 신규/변경 기록만 읽고 성공한 빈 조회도 캐시한다. 직접 save·import·비활성 화면 재진입에는 보수적으로 다시 조회한다.
- 초기 모든 테이블을 캐시 목적으로 추가 읽지 않는다. 첫 화면 준비에 필요한 세션부터 사용하고 안전성 검사는 생략하지 않는다. 저장소 개방·전체 검사·위젯의 저장된 snapshot 조회는 소유한 별도 context의 executor에서 처리한다.
- 현대 첨부 전체 검사는 bootstrap worker에서 실제 decode·MIME·크기·SHA-256 검증을 유지하며, 같은 attachment의 성공 metadata만 그 검사 안에서 재사용한다. 레거시 이미지 이관도 같은 detached 생성·호출 경계의 private context에서 수행하고, 전체 수렴과 이미지 변경을 최종 1회 save에 포함한다. 오류·취소 시 모두 rollback하며, 기본 공개 이관 API의 pending-edit checkpoint·회고별 save·부분 성공은 유지한다. 누락·거부·보류는 Sendable report로 root에 전달해 재이관 없이 경고를 유지한다.
- iOS Intent handler는 App.init에서 즉시 등록하되 저장 명령은 동일 startup single-flight를 await한다. scene이 없는 background Intent도 준비를 진행하며, 검사 완료 후 fresh UI context를 화면과 Intent/Watch 후속 조정에 전달한다. 준비 전에 모델을 수정하지 않는다.
- cold URL은 opening/recovery부터 App의 handler가 Session에 URL 값만 FIFO로 보존하고, ready root가 최초 task·revision 변경에서 1회 consume한다. 재시도와 scene caller 취소는 큐를 지우지 않는다. 전용 4개 검사를 포함한 Debug 803개·Release 767개 검사와 최종 플랫폼 게이트가 통과했다. Mac stopped OS cold URL은 후속 frozen515 correctness005에서 확인했으며 iPhone의 실제 전달은 대기 중이다.
- 기본 저장소의 레거시 copy/restore는 기존 factory MainActor 경로로 남는다. 이미지가 많으면 background 검사·이관도 보드 준비와 cold Intent 명령의 대기 시간에는 포함된다. MainActor 분리만으로 전체 ready 시간이 없어지거나 첫 frame 목표를 달성했다고 판단하지 않는다.

## 진행 기록

- 기존 사용자 변경을 보존한 후 세 영역(시작 경계, 저장 후 무효화, 입력어)을 독립 검토했다.
- 이미 적용된 비활성 탭 조회 차단, 위젯 150ms 병합, 진행 기록 80ms debounce를 유지하고 추가 개선만 비교한다.
- 초기 조사에서 발견한 MainActor 실행 경로는 병목 후보이며, 이번 계측 없이 원인 확정으로 기록하지 않는다.
- 첫 관련 검사에서 새 이월함 테스트의 임시 ModelContainer 수명과 startup 테스트의 UTC legacy 날짜 기대값 문제를 발견해 수정했다. 이 실패 로그는 보존하고 수정 후 재검사를 진행한다. 위젯 reader 6개와 입력어 캐시 9개는 먼저 통과했다.
- V1~V11 및 compatibility 파일 12개의 SHA-256이 작업 시작 시 보존한 사용자 소스와 같음을 확인했다. 기존 사용자 모델 변경을 덮어쓰지 않았다.
- SwiftData actor를 detached에서 생성한 뒤 MainActor에서 직접 호출하면 물리 스레드가 main인 원시 probe 결과를 확인했다. actor isolation 자체를 background thread 보장으로 해석하지 않는다. 앱은 생성과 호출을 같은 detached 안에서 수행하며, 이 실제 경계를 테스트 helper로 공유했다. 생성/실행 probe가 모두 false(main 아님)이고 commit 전 thread assertion, 주입 실패 뒤 같은 worker 재시도, 실제 읽기 전용 저장소의 최종 save 실패 뒤 rollback 검사가 통과했다(`candidate-bootstrap-facade-tests.log`).
- 이전 읽기 전용 오류 코드 가정은 이 SDK의 실제 `NSCocoaErrorDomain` 513과 달랐다. 관측한 `fileWriteNoPermission`과 error graph를 정확히 검증하도록 수정했다. 과거 실패 로그는 보존했다.
- `candidate-related-image-tests.log`의 최종 결과가 관련 159개 검사 PASS / 3.969초임을 확인했다. 격리된 UUID temporary directory의 실제 PNG·누락·손상·중복·10장 보류, 현대 첨부 무결성 유지, off-main read/inspect, 두 회고의 최종 save 주입 실패 후 전체 rollback·같은 worker 재시도, 실제 취소 플래그 후 rollback, Session report/import 집계 8개가 모두 통과했다.
- 두 normalized JSON을 다시 대조해 42개 조건 키·조건별 n20와 이월 360개 canonical SHA-256/inbox count 쌍 일치를 확인했다. `core-comparison-table.md`의 값은 raw 표본에서 재계산한 통계를 사용한다.
- 마지막 lifecycle 검토에서 opening 중 cold URL handler가 ready Root에만 있는 공백을 발견해 URL 값 버퍼를 추가했다. 이 후속 소스는 앞선 159개 PASS 이후 변경이므로, 4개 전용 검사와 동기화한 진단 복사본·shipping source의 다음 전체 게이트를 최종 증거로 사용한다. commit 전 writer 설치나 startup single-flight 중복은 현재 호출부에서 발견하지 못했다. Root가 없는 background 실행의 ready 후 import 수렴은 여전히 foreground root의 handoff에 의존하며, 실제 작업 오류는 재현하지 않았다.

- URL 후속 변경 전 첫 전체 게이트의 Debug 799개 검사 PASS / 28.626초는 `full-regression-before-cold-url-cancelled.log`에 보존했다. 새 URL 소스를 최종 검증에 포함하려고 Release build 중 의도적으로 중단했으며 종료 코드는 130이다. 전체 게이트 PASS로 계산하지 않는다. 후속 전체 실행은 `full-regression-gate.log`에 보존했으며 실제 UI cold URL 전달 재현은 대기 중이다.

- 최종 URL 소스를 포함한 `./scripts/verify-platform-builds.sh`가 종료 코드 0으로 완료됐다. Debug 803개 검사 27.030초, Release 767개 검사 25.016초와 플랫폼·내장 번들·privacy 검사가 모두 통과했다. 현재 실행을 과거 중단 로그와 구분한다. 스키마 V1~V11 및 compatibility 12개 파일의 작업 시작 SHA-256 일치도 다시 확인했다(`schema-compat-preservation-current.json`).

- 양 플랫폼 행 보완 후 같은 전체 게이트가 종료 코드 0으로 완료됐다. 실제 로그에서 Debug 803개 검사 26.522초, Release 767개 검사 24.613초와 Mac Debug·Release 빌드 끝부분을 확인했고, 로그 SHA-256이 `full-regression-after-row-fix-gate-result.json`의 값과 일치한다. iOS/macOS Debug·Release 및 내장 Watch·위젯 식별자·실행파일·privacy 검사를 포함한다. 행 보완 소스 SHA와 스키마·compatibility 12개 파일의 일치 증거는 해당 결과 JSON 및 `schema-compat-preservation-after-row-fix.json`에 보존한다. 이 게이트에는 native UI·기기 실행이 없으며 Mac 진단 앱 동작·native trace의 후속 검증은 위 별도 증거와 구분한다. 실제 읽기 전용 편집 실패·초안, native URL 전달·frame·동작별 main-thread와 물리 iPhone 검증은 미완료로 유지한다.

## 현재 확인된 결과

코어 동일 조건 비교에서는 반복 입력어·필요 없는 이월 재조회 비용 감소를 확인했고, 이월 결과 360개 쌍이 같다. 일반 제목 입력 자체는 약 0.001ms로 제목 검색이 일반 생성·삭제 지연의 주원인이라는 근거는 없다. 시작의 전체 검사·레거시 이미지 작업을 UI context 설치 전 background 경계로 이동했으며 관련 검사와 행 보완 후 전체 플랫폼 게이트가 통과했다. 후속 제출 API 변경을 포함한 shipping 전체 게이트003도 Debug 812개·Release 775개 및 플랫폼·내장 번들 검사를 통과했다. native UI·실기기 실행은 이 게이트에 포함하지 않는다. iOS simulator의 native `ApplicationFirstFramePresentationResponsive` p50은 64.2% 감소했지만 그 frame의 보드 내용 준비 완료를 입증하지 않는다. 이월함이 빈 iOS UI 조건의 작업 동작 시간은 거의 같다. Mac 기준·후보 실제 CUA 동작 n20은 일반 생성 p50 +2.5%, 입력어 생성 +11.3%로 작업 지연 개선을 입증하지 않는다.

후속 입력어 제출 API는 전체 표시 목록 구성 대신 최신 제출 대상과 연결 항목을 조회한다. 1,000개 템플릿의 반복 n20에서 정확 입력 p50은 118.736→36.902ms, 선택 입력은 111.352→2.948ms였으며 저장 결과 92개 쌍이 같았다. 이는 함수·저장 경계의 비교이고 실제 입력→표시 시간은 아니다. Mac의 실제 readonly 최종 save 실패 두 번, 별도 root 갱신 한 번, 초안 유지 및 취소→계속 작성은 확인했다. 후속 frozen515 correctness005에서는 background→active root 갱신 뒤 초안 보존과 버린 뒤 원본 편집 재개를 확인했다. strict inactive→active·NSApplication didBecomeActive 관측은 남아 있다.

기존 Mac CRUD trace의 저장·export·streaming 검토는 끝났으나 동작별 native 시간축 대응·연속 main stall은 미확인이다. 후속 Mac recorder014는 matched repeat10의 좁은 native 구간 통계를 확보했으나 첫 보드 frame·전체 시작 시간이나 CPU 인과를 확정하지 않는다. iPhone 실제 OS cold URL 및 실기기 실행도 남았다. Mac stopped OS cold URL은 후속 frozen515 correctness005에서 확인했다. 실기기는 격리된 서명 복사본을 준비했지만 잠금 때문에 설치·XCTest 전에 중단됐다. 설치 앱의 지연 해결 또는 100ms 초기 피드백 달성을 확정하지 않으며, 과거 최적화 수치나 build 번호 일치를 이번 개선의 성능 증거로 사용하지 않는다.
